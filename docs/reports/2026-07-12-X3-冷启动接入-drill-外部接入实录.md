### 步骤①：capability schema 条目

- **docs 自足度：中。** `capability-contract.md` [S-1] 把事实记录 SHAPE 讲得**很全**（id/kind 闭合枚举/implies/conflicts/params/provenance/trust），[S-2] 关系语义清晰，profiles.md 给了 profile 写法。我据此写出了 scratch 的 `demo.mac` 事实（见 `demo-capability-fact.attempt.json`）。
- **卡壳 1（★重）：schema 是 aspirational、与代码分叉。** `schema/capability.schema.v1.json` 的 `$meta` 明文：这些字段（provenance/trust/subclass/闭合 kind 枚举/命名空间 params/可序列化插件签名）**"grep=0 in code today; code and schema.def are intentionally divergent"**。即：**照 spec [S-1] 写出的能力事实，当前代码并不消费**。盲适配者读 spec（把 [S-1] 当契约）**无从得知**代码用的是另一套/更旧表示——只有翻那条埋在 14KB JSON 里的 `$meta` note 才发现。这是 external-followability 的**结构性陷阱**（docs gap #2）。
- **卡壳 2：事实实例写进哪个文件、无 doc 指名。** [P-2]/[F-3] 说「capability fact rows 属 tables」，但**没有一份 doc 命名"事实实例表"文件**。`capability.schema.v1.json` 是 shape 不是实例。盲适配者不知道 `demo.mac` 该落哪——须去 grep 或读 RVV/IME 内部（禁）才能定位事实实际注册点。**盲纪律压力点 #1。**
- 交付对照 [P-2]①「facts+relations 表行」：**shape 可跟；落点不可跟。**

### 步骤②：plugin 注册

- **docs 自足度：低。** `interfaces-and-registry.md` + `locality-contract.md` 讲清了 registry **职责**（lookup/orchestration only、不得从 plugin 名派生计算）与「tcrv-opt 构造 `ExtensionPluginRegistry`、装入 built-in 插件」的**概念**。但**没有一步说「把你的插件注册调用加到哪个文件的哪一行」**。
- **卡壳（★重）：注册点 = 共享文件、非家族局部、无 doc 指名。** 实际注册site = `lib/Plugin/Builtin/BuiltinExtensionPlugins.cpp`（`registerBuiltinExtensionBundlePlugins`），并被 `tools/tcrv-opt/tcrv-opt.cpp` / `tcrv-translate.cpp` 引用。公共头 `include/TianChenRV/Plugin/BuiltinExtensionPlugins.h` 只暴露聚合函数签名、不含"怎么加一个新家族"。要落地注册，我**必须编辑 `BuiltinExtensionPlugins.cpp`**——一个**非家族局部的共享文件**。这直接与 [F-3]「家族接入 PR **contained to `plugins/<family>/` + table rows + docs**、无 core 文件编辑（[P-1]）」矛盾。docs 全域 grep `registerBuiltin`/`ExtensionPluginRegistry` 只命中 IME-gating **报告**与 locality-contract 的**泛述**，**无"注册你的插件在此"的可跟步骤**（docs gap #3）。
- 交付对照：注册不在 [P-2] 五件里显式列出，却是**缺它就跑不起来**的隐形第六件。

### 步骤③：falsifier 家族条目

- **docs 自足度：中。** `FALSIFIER-INDEX.md` 把 [F-1..F-6] → checker/lit/gtest/CI job 映射得**很清楚**，且指出新家族要碰的 schema：F-1 零分支门读 `schema/family-regex.v1.json` 的 core_scope、F-3 收容门读 `schema/family-manifest.v1.json` 的 per-family `source_ranges`、F-6 独立家族要闭包 ∩ `rvv.*` = ∅。
- **卡壳：给的是"门在哪"、不是"新家族加哪些行"。** INDEX 是**门 → 工件**的索引，不是**"接 DemoAccel 时往 `family-regex.v1.json`/`family-manifest.v1.json` 各加什么行"**的填空指引。盲适配者得逆向读现有 JSON 条目照猫画虎（这些 JSON 是声明工件、可读，非 impl），friction 中等、可自解，但**不是 [P-4] 意义上的"followable procedure"**。
- **正面：** falsifier 组本身（六门全进 CI）是 C1「机检验收」最扎实的一面；一旦家族条目加对，绿/红是机器判的、不靠人肉。
- 交付对照 [P-2]④「tests」：lit byte-exact + per-board objdump golden 的**要求**清楚；**模板/骨架无**（见步骤⑤）。

### 步骤④：selector 骨架

- **docs 自足度：中高（本步 docs 最强）。** `generation-selection-tuning.md` 的 [SEL-1] 两段式选择器（合法性过滤 → 排序：实测 memoized argmin / 冷启动能力先验层）、[SEL-2] 硬时序、[D-4] 三级归因（reason ∈ {only_feasible, static_order, prior, measured} 为主键）、Gearbox 复用契约（「新增可调 op = adopt interface，不新写 pass」）讲得**清楚且自洽**。盲适配者能明白：DemoAccel 只需实现 `estimateVariantCost` hook + 声明能力先验，core 的 walk-all pass 自动发现，**不改选择器 core**。
- **卡壳：hook 的具体签名不在 docs、在 30KB 头。** `estimateVariantCost` / `realizeSelectedVariantBody` 的**实际 C++ 签名**在 `include/TianChenRV/Plugin/ExtensionPlugin.h`（30KB，[P-1] 说接口签名"reference by ID"、docs 不重抄）。要真写 override，我须读该头（公共 API 头、非 RVV impl，属可读边界）——但**这仍是 docs→源的落差**：契约有、可编译的签名无（docs gap，轻）。
- 交付对照：selector 属 wiring 非 construction，docs 明确；本步是**协议最 followable 的一件**。

### 步骤⑤：接入实录（[P-4] 集成文档）

- **docs 自足度：低（无模板）。** [P-4] 强制「integration doc」为 C1 从 in-house demo 升格 protocol 的判据，但**全仓无 [P-4] 集成文档的可填模板/骨架**。适配者知道"要写一份"，但没有"照这个 skeleton 填"的东西——本报告即是被迫从零构造的第一版（docs gap，中）。
- 交付对照 [P-2]⑤「ledger 条目」：C2 成本账本（core LOC / plugin LOC / new caps / new ops…，见 locality-contract §Evaluation Metrics）的**字段**列出清楚；**落哪个账本文件**同样未指名（与步骤①同病）。

## 3. 「五件套」实际触碰集 vs docs 声称（★最大 gap 的量化）

docs 反复讲「五件套 = 5 个文件、[F-3] contained to `plugins/<family>/`」。**实测：参考范本 `Template/` 家族的真实触碰集 = 6 个目录根、~20 文件、6 个 CMakeLists**（不含注册点那第 7 个共享文件编辑）：

```
include/TianChenRV/Dialect/Template/IR/   TemplateDialect.h, TemplateOps.td (+2 CMake)   ← 方言 ops/types，五件套未列
include/TianChenRV/Plugin/Template/       4 headers
lib/Dialect/Template/IR/                  TemplateDialect.cpp (+2 CMake)                  ← 五件套未列
lib/Plugin/Template/                      5 cpp (+1 CMake) = 名义"五件套"
lib/Target/Template/                      TemplateTargetSupportBundle.cpp (+1 CMake)      ← 五件套未列
lib/Plugin/Builtin/BuiltinExtensionPlugins.cpp   注册点（共享/core-ish，编辑违 [F-3]）    ← 五件套+[F-3] 均未列
test/Plugin/                              lit + gtest
```

盲适配者照「复制 5 文件」起步，**第一次 `cmake --build` 就撞** `TianChenRVTemplateDialect` / `TianChenRVTemplateTarget` 链接目标缺失——而这两个目标对应的 4 个目录（Dialect/IR + Target + 两个 include 侧）**五件套一字未提**。[F-3] doc 自己承认这是 aspirational（「conditional on the structural premise that family code is actually gathered under `plugins/<family>/`; where a family's code is still scattered, consolidating it is the prerequisite work」）——即**收容前提当前对 Template 范本本身都不成立**。这是 external-followability **单个最大的 gap**：五件套/[F-3] 的"局部性"叙事与真实跨 6 根的触碰集**系统性不符**。

## 5. external-followability 判读

**判读 = ②「部分需 peek / docs gap 具名」——协议在"概念/契约层"强，在"可跟落地层"有系统性缺口。**

- **强的半边（真 C1 证据）**：协议的**不变量与契约**（能力事实 shape [S-1]/[S-2]、registry 职责边界、[SEL-1] 两段式选择器 + [D-4] 归因主键、falsifier 六门机检、[P-1] 冻结接口、typed-body→route→EmitC 标准流、locality core/plugin 分工）**成文、自洽、可判**。一个盲适配者能**正确理解协议的形状与红线**，不必读 RVV 内部即可讲清"接一个家族要满足哪些不变量"。这本身是**非平凡的 C1 证据**：协议的*判断依据*是外部可读的。
- **弱的半边（gap）**：从"理解协议"到"落地一个能编译的家族"之间，**缺可跟的落地层**——三份互斥"五件套"、五件套严重**undercount**真实触碰集（6 根/~20 文件 vs 声称 5 文件）、注册点是**未文档化的共享文件编辑**（且违 [F-3] 自身收容主张）、schema 是 **aspirational 且与代码分叉**（照 spec 写的事实代码不消费）、无 [P-4] 集成文档模板。这些不是"读 RVV 内部就能补"的知识——是**协议 docs 本身缺的 procedure**，正落在 [P-4] 判据的反面。
- **净结论**：C1 的「协议本体存在且外部可读其**契约**」成立；「协议对无内部知识第三方**自足到能独立落地一个家族**」**尚不成立**——落地层需 3-5 处具名补强。头牌主张宜**收窄措辞**为「协议的*判断依据*外部可跟（强）；协议的*落地步骤*当前仍需内部知识补全（欠账已具名）」，而非无条件「可复制扩展接入协议」。

## 6. docs gap 具名清单

**Top-3（按对 external-followability 的伤害排序）：**

1. **[GAP-X3-TOUCHSET] 五件套 undercount 真实触碰集**（§3）：docs 讲 5 文件 / [F-3] `plugins/<family>/` 局部性，真实 = 6 目录根 / ~20 文件 / 6 CMake + 1 共享注册文件；照 docs 起步必撞缺失的 Dialect/Target 链接目标。收法：给出「一个家族的完整触碰集清单 + CMake 六目标依赖图」，或明记 [F-3] 局部性为**目标态、非现状**并给现状触碰集。
2. **[GAP-X3-REGISTER] 注册步骤未文档化且违 [F-3]**（步骤②）：接入必编辑共享 `lib/Plugin/Builtin/BuiltinExtensionPlugins.cpp`，无 doc 指名此步；与 [F-3]「无 core 文件编辑」矛盾。收法：写一条「注册你的家族在此文件此处」的可跟步骤，并裁定该文件是否算 core（若算，[F-3] 措辞须让路一个"注册表行"例外）。
3. **[GAP-X3-SCHEMA-DIVERGENCE] spec 能力 schema 是 aspirational、与代码分叉**（步骤①）：照 `capability-contract.md` [S-1] 写的事实当前代码不消费，仅 `capability.schema.v1.json` 的 `$meta` 埋着这条真相。收法：在 capability-contract.md 顶部**显著**标注"[S-1] 描述目标 schema；当前代码消费的实际表示见 X，分叉是 tracked gap"，别让盲适配者按 aspirational 契约白写。

**其余具名 gap：**

4. **[GAP-X3-FIVEPIECE-COLLISION] 三份"五件套"枚举互斥、都称 [P-2]**（F0）：交付轴 vs 文件轴 vs 仓库轴，缺一张互映表。
5. **[GAP-X3-FACT-LOCATION] 能力事实/账本实例的落点文件无 doc 指名**（步骤①/⑤）。
6. **[GAP-X3-NO-P4-TEMPLATE] 无 [P-4] 集成文档可填模板**（步骤⑤）。
7. **[GAP-X3-DISCOVERY] README 不指向接入协议图**（§7）：README §「Repository layout」是泛目录，**不提** Template 范本 / 五大件图 / 接入路径；而 `REPOSITORY-MAP-五大件.md` §4「30 分钟定位路径」却假设"从 README 的 Repository layout 起"。盲适配者读 README **发现不了** `docs/method/REPOSITORY-MAP-五大件.md`，须自己 grep `.trellis/spec` + `docs/method` 才找到协议图。**入口断链**——外部适配者连协议 docs 在哪都得靠运气。
8. **[GAP-X3-HOOK-SIG] 选择器/realize hook 的可编译签名不在 docs**（步骤④，轻，[P-1] 有意 by-ID）。

## 7. 附：入口可发现性

`README.md` 是外部人第一入口，但它既不含"如何接一个新家族"，也不链到 `REPOSITORY-MAP-五大件.md` / `FALSIFIER-INDEX.md` / `.trellis/spec/plugin-protocol/`。协议图自己写的"30 分钟定位路径"起点（README Repository layout）在 README 侧是断的（[GAP-X3-DISCOVERY]）。**建议**：README 加一节「Extending the stack: add a family」直链五大件图 + plugin-protocol spec + Template 范本。此为 external-followability 的**零步**，当前缺。

## 8. X3 证据标准建议（★必问 · 供主会话 flag 用户 · 我只建议不定标）

**盲-agent-drill（本报告）是否够格算 C1 [C1-4] 的"外部接入实录"证据？还是需真第三方？** 我的诚实评估（**判定权归用户**）：

- **本 drill 够格的部分**：作为**协议 gap 的探针**，盲-agent-drill **有效且省成本**——它已具名 8 个 gap、量化了触碰集 undercount、暴露入口断链，这些是真第三方也会撞的、且现在就能修。作为「协议*契约层*外部可读」的证据，drill 足够。
- **本 drill 不够格的部分**：作为 [C1-4]「可复制*协议*」的**正面兑现**证据，盲-agent-drill **有先天偏置**——(a) 我与协议作者**同栖一个仓库上下文**（读得到 spec/schema/Template，真外部人可能连仓库结构约定都不共享）；(b) 我**未真 build/link 一个家族到绿**（drill 是可逆、禁改主树），"能编译能过 falsifier"这最硬的一环没兑现；(c) agent 的"盲"是**规则约束的盲**、非**知识真空的盲**，我对 MLIR/编译器惯例的先验远超一个随机第三方。
- **建议的证据标准分层**（供用户裁）：**盲-agent-drill = "gap-探针 / 协议 pre-flight" 级证据（本报告归此级）；[C1-4] 正面兑现须一次真接入到"build 绿 + falsifier 六门绿 + 触碰集符合 [F-3]（或明记偏离）"**——理想由**真外部第三方**跑（最强），退而求其次由**一个未参与协议编写、仅给 docs 的 in-house agent 真 build 到绿**（比本 drill 强、比真第三方弱）。本 drill 建议登记为 [C1-4] 的**"gap 清单 + pre-flight"证据**，不当"协议已兑现"结论。
