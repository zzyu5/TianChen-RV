## 一、[GOV-8] iq3_s 格式事实（全部自核 ggml + 机器核对，未照抄 brief）

来源 = `/home/kingdom/phdworks/llama.cpp/ggml/src/ggml-cpu/quants.c` 的
`ggml_vec_dot_iq3_s_q8_K_generic` + `ggml/src/ggml-common.h` 的 `block_iq3_s`。

| 轴 | iq3_s 实测事实 | vs iq3_xxs |
|---|---|---|
| grid | `uint32_t iq3s_grid[512]` | **512**（xxs 256） |
| entry width | uint32 = 4 grid 字节 → **每组 2 entry** | **同**（I32x4） |
| grid index | **9 bit**：`qs[e] \| (((qh[ib]>>e)&1)<<8)`，0..511 | 不同（xxs 是裸 u8） |
| sign | **显式 `signs[QK_K/8]` 平面**，`signs[l] & kmask_iq2xs[j]` | **不同**（详见 §二） |
| ls | **Single**，每 32 元素子块 1 个 | 同 |
| fold | 单 i32 累加器 `bsum += sumi*ls`；`sumf += d*bsum` | 同 |
| store | **`*s = sumf` —— 无常数** | 不同（xxs 是 `0.25f`） |
| block | 110 B = d fp16@0 + qs[64]@2 + qh[8]@66 + signs[32]@74 + scales[4]@106 | 无 double-duty 区 |

**机器核对（不是"提取时已验证"的口头承诺）**，命令可原样复跑：

```
oracle iq3s_grid   == ggml  : True
in-tree kIQ3SGrid  == ggml  : True     (全 512 项)
oracle kmask_iq2xs == ggml  : True [1, 2, 4, 8, 16, 32, 64, 128]
grid byte range: min=1 max=15 -> grid*sign fits int8: True
```

最后一行是**真正的正确性前提**：leaf 把 sign 乘到 grid 字节上（`vmul_vv_i8`），
要求每个 grid 字节 < 128。iq3_s 全部 ∈ [1,15]（全奇数），远低于 iq3_xxs 的 62。**已查，非假设。**

**累加器个数自核 = 1**（iq3_xxs 也是 1；iq1_m 是 3）。`sumi` 在子块内被 `bsum += sumi*ls` 折掉，
`sumf += d*bsum` 是浮点，`*s = sumf` 是 store。所以块末整数量只有 `bsum` 一个。
oracle 另加 ls-**无权** `sumi_raw` 做**故障分离**（非 ggml 量，用于让 ls 故障与 grid 故障不混叠）。

## 二、★sign 平面发现（本役最重要的一条）

**iq3_s 的 sign 编码不是 iq3_xxs 的，而是 iq2_s 的。**

- iq3_xxs：`signs = ksigns_iq2xs[(aux32 >> 7*l) & 127]` —— **7 bit selector** 经表展开成 8 bit mask。
- iq3_s：`signs[l] & kmask_iq2xs[j]` —— **block 自带的显式 8 bit 字节直接测位，无 ksigns 间接层**。
  这与 `ggml_vec_dot_iq2_s_q8_K` **逐字相同**。

⟹ **用的 enum 值 = `GridSignPlane::Signs256`（既有值，iq2_s 的行在用，非新值）**，
命名的表 = **`weft_iq2s_signs256`（复用 iq2_s 的 decl，未克隆）**。

**为什么复用是事实而非偷懒**：该 ±1 平面是 `(byte b, lane j) -> (b>>j)&1 ? -1 : +1` 的**纯函数，不含格式信息**。
再发一份字节相同的 2048 B 表挂 iq3 名字 = copy，不是关于 iq3_s 的事实。
（与 iq3_xxs 复用 signs64 的理由同构，但**根据不同**：xxs 是因为 ggml 两个格子**字面读同一张表名**；
iq3_s 则是**构造性**的 —— ggml 的 iq3_s 根本不读任何 sign 表。）

**新值有真行使用吗？** —— **本役没有引入任何新 enum 值。** Signs256 由 iq2_s 早已在用。

**gather 算术完全相同**（`table[b*8+j]`，shift 3）：Signs64 vs Signs256 只差**表名与表长**，
所以 plan 用 data 承载它，leaf 一行分支都不需要。**这正是"axes 是否 span 家族"的判据点。**

## 三、★leaf 复用 vs 新建 —— 判据与结论

**结论：复用 iq3_xxs 的 dual-entry leaf，参数化，不新建。**

**判据 = 「哪个键上真的不同」，逐键查**：

| 键 | iq3_xxs | iq3_s | 是否 leaf 键 |
|---|---|---|---|
| `entryWidth`（选 leaf 的键） | I32x4 | **I32x4** | **相同 ⟹ 同一 leaf** |
| nest 形状（每组 2 base + 激活区间劈半 j/4, j%4） | 有 | **同** | 相同 |
| 累加器数 | 1 | **1** | 相同 |
| sign gather 算术 | `tbl[b*8+j]` | **同** | 相同（只差表名 = data） |
| **grid index 条宽** | u8 + vzext | **u16 + vle16** | **不同 → 但是 DERIVED 参数** |
| **store 常数** | `0.25f` | **`1.0f`** | **不同 → 但是 DATA** |

两处差异**都不改 nest 形状**，且都不是独立轴：
- 条宽由 **`gridIndexStripIsU16(gridEntryCount) = gridEntryCount > 256`** 派生（新增 `constexpr`，
  与既有 `gridEntriesPerGroup`/`gridEntryByteShift` 同类，两字段不可能互相打架）。
  **该谓词与全部 6 个既有行一致**（256→u8：iq2_xxs/iq3_xxs；512/1024/2048→u16：iq2_xs/iq2_s/iq1_s/iq1_m）。
- store 常数早在 C4a-4 就已是 data（`storeScaleLiteral`），本役**直接兑现了那个决定**。

**反证（为什么条宽不是 leaf 键）**：条宽与 leaf 边界**正交**，registry 自己就是证据 ——
iq2_xxs（Single, 256, u8）与 iq1_s（Single, 2048, u16）**分属不同 leaf，但原因是 foldArith，与条宽无关**。
C4a-5 之前每个 leaf 恰好只带条宽一致的行，所以都能硬编码；dual-entry leaf 是**第一个带上两个条宽不同的行**的 leaf。

**若新建 leaf 反而会坏事**：dispatcher 第 3 步是 `entryWidth == I32x4`。两行同为 I32x4，
新建第二个 leaf 就必须再引入一个**新的选择键**（gridEntryCount 或 decode_model 字符串）——
后者正是 C4a 用 registry **消灭掉的手工字符串链**，属于结构性倒退。

**已警惕 brief 点名的陷阱**（"看起来只差 grid size"）：iq3_s 与 iq3_xxs **并非**只差 grid size ——
sign 平面这一轴上它站到了 iq2_s 那边。**该轴已被 oracle 的 `SIGN7BIT` 负控单独钉死**（见 §六）。

leaf 已改名 `emitRepackGem{v,m}Iq3XxsQ8K` → **`emitRepackGem{v,m}GridDualEntryQ8K`**（服务两行，旧名会说谎）。

## 四、★store 常数：为什么写 `1.0f` 而不是留空（含明确的取舍与代价）

ggml 是 `*s = sumf`，无常数。两种诚实写法：`"1.0f"`（发射乘法）或 `""`（不发射）。**选前者**，理由**不是风格**：

- **空串正是「SignScaleStore 行忘填 storeScaleLiteral」的样子。** 现在 leaf 遇空串**拒绝发射**（fail-closed）；
  若教它"空 ⟹ 不发射乘法"，这个错误就从**响亮拒绝**变成**静默发出未缩放的 store** —— 用一条真门换一条指令，亏。
- 加第二个字段（"有无 store scale"）= 两个可漂移字段，正是 `gridStoreScaleRole` 存在要堵的隐患。
- `*s = sumf` ≡ `*s = 1.0f * sumf` 在 IEEE-754 下**精确相等**，所以 `1.0f` 是对该常数的**忠实 C 渲染**，不是虚构。

**代价如实记**：emitted C 每个输出条多一次 `vfmul_vf_f32m2(sumf, 1.0f, vl)`，**冗余**。
位置在 **per-strip store，block 循环之外**（这是从 emit 读出的事实，非性能主张）。

**关键：这不是未经测试的因果断言。** oracle 的 REFERENCE 走 ggml 的裸 `sumf`，
EMITTER-MODEL 走 `1.0f * sumf`，二者差异被**逐列实测**：

```
worst fp norm (ggml `*s = sumf` vs emitted `1.0f * sumf`, reported only): 0.000e+00
```

新增 role `unit_scale`（CLOSED map；空串仍无 case ⟹ 仍拒绝）。

## 十二、★第三次错误预测（已由落地证伪并记档）

C4a-4 的 [D-1] 探针注释预言 iq3_s 需要 **"DUAL ls (ls1/ls2 from the scales nibbles)"**。**错。iq3_s 是 Single。**

ggml 每次迭代确实读 `scales[ib32/2]` 的两个 nibble 并命名 ls1/ls2 —— 但循环 **`ib32 += 2`**，
ls1 用于**整个**子块 ib32 的 4 个组，ls2 用于**整个** ib32+1。**每 32 元素子块 1 个 ls = Single**；
一个 scales 字节装的是**两个子块**的，那是 packing 不是 arity。
（对照真 Dual：iq2_s 在**同一个** 32 元素子块内 ls1 管组 0-1、ls2 管组 2-3，粒度 16 元素。）

**三次错误预测的共同结构（与 brief 前科 9 的洞察完全一致，且本役是第三例）**：
| # | 预测 | 真相 | 位置 |
|---|---|---|---|
| 1 | iq3_xxs 需要 `GridSignPlane::Ksigns128` | 不需要，复用 Signs64 | **注释** |
| 2 | iq3_xxs 需要 `GridEntryWidth::I32x4`（说得像那是阻塞点） | 值只有三行，真成本是 leaf | **注释** |
| 3 | **iq3_s 需要 DUAL ls** | **Single** | **注释** |

**三次全在注释里，一次都没在 enum 里** —— "无真行使用不写 enum 值"的规则**从未失守**，
投机每次都搬到规则不看的地方。且**三次都源于读 ggml 的【变量名】而非它的【循环步长/算术】**。
本役已把该规则**同样施加到探针注释上**（探针现在只断言机制，不预言下一格）。
