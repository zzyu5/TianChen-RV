## 三、★ 核心发现：两条事实通道必须分开报（易误读）

这是本轮最重要的机制发现，**直接影响表怎么读**：

| 通道 | 载体 | 是否进 `declared_instance_hash` |
|---|---|---|
| **(1) in-IR 事实通道** | IR 里的 `weft.exec.capability` 事实行 → `TargetCapabilitySet` | **进**。改事实行 → hash 变。 |
| **(2) `march=` pass-option 通道** | 前门 pass 选项 → `deriveMinimumVLEN()`（`lib/Plugin/RVV/RVVCapabilityProfile.cpp:290`） | **不进**。march 不是 in-IR 能力事实。 |

**实测钉死**（P4 探针，真实输出）：同一份 SEL-1 fixture，`march=rv64gcv` vs `march=rv64gcv_zvl256b` → `minimum_vlen` 128→256、chosen LMUL **m2→m1**（reason=`prior`），但 **`declared_instance_hash` 两边完全相同**（`842c4a01e778...`）。

> **禁误读**：不能说「两个板 ⇒ 必然两个 instance-hash」。**只有 in-IR 事实分化才给出两个 hash**；march 通道给出的是同 hash、不同选择。本表因此**两条通道各出一个探针**，不混报。

schema 自身对此有明文（`schema/capability.schema.v1.json:208`）：declared-instance-hash 取在 profile **展开后的事实集**上。

### C2 非空洞性验证（负控，已实跑）

`strip_fact_regions()` 若把整个文件剥空，C2 会**平凡通过**。已做负控证伪：

```
NEG CONTROL 1 -- stripped remainder is non-empty (not vacuous):
  contains rvv_typed_body : True
  contains ime_keyed_body : True
  contains vlen_bits fact : False (must be False)
  equal across boards     : True (C2 PASS)
NEG CONTROL 2 -- perturb body lmul m1->m2 in ONE variant:
  equal across boards     : False (must be False => C2 can FAIL)
```

**保留 body 体量 = 工具自发（非转抄）**，权威值取 `--check` 的 C2 行 evidence：

```
$ python3 tools/visibility/t1d_dual_instance.py --check
C2-fact-confined-diff | PASS | non-fact surface byte-identical;
  sha256(stripped)[:16]=65320bac3b27ebb4; retained body: chars=1256 lines=25
  (emitted, not transcribed)
```

→ 剥离后**保留 1256 字符真 body（含两个变体）**、**不含事实字段**；且**改 body 一个字节 C2 立刻 FAIL** ⇒ C2 有真判别力，非平凡真。

> **★订正记录（§四.3 独立复核抓出·2026-07-17）**：本节初稿写 `chars = 1237`，**不可复跑 = 违「0 造数：任何数字须机算可复跑」**。定案经过：复核代理独立重算得 **1256**；主会话再独立重算得 **1198**——**三方三个数**。根因 = **该数无钉死的推导路径**（C2 剥的是**生成的实例文件**，而 1237/1198 各自重建了不同的 body；主会话的 1198 亦为错误重建）。**修法 = 把该数改为工具自发**（`core_diff_checks()` 的 C2 evidence 现直接 emit `chars/lines`），转抄链就此消灭；权威值 = **1256/25**（工具输出·`--check` 复绿✓）。原 `lines = 25` 属实、未变。**该数低报**（1256 > 1237）故不夸大非空洞性、不影响任何 verdict —— 但仍按红线订正，不因"方向无利"放过。

## 六、诚实边界（禁粉饰）

1. **零性能主张**。本表全为编译期结构事实。`reason=prior`（P4）是 [SEL-1] 的**填充率结构论证**（utilization），**不是** perf 判决。不碰 perf-covered 9/83。
2. **P4 的 m2/m1 翻转是 emit 形态分化，不是"赢"**。既有 fixture 头注已自钉「NO perf claim: this is a STRUCTURAL fill argument」。本报告沿用该口径。
3. **本表的双板事实是"声明实例"，非板上实测**。`fact_vlen_bits=128/256` 是 IR 里声明的能力事实（rvv 板 VLEN128 / k1 板 VLEN256 与真硬件一致，见 memory `hardware-test-access`），但**本表未 `ssh rvv` / `ssh k1` 跑硅**——T1d 按设计就是**板无关·结构**表（`实验总纲v1.md:52` 明列「板无关·结构」），不需要硅。**不得**把本表读成硅上证据。
4. **`@ime_keyed_body` 是为演示构造的探针变体，不是出货 kernel**。它证明的是**选择机制键控事实**，不是某个真实 IME kernel 的部署。真 IME 部署证据在别处（memory `k1-ime-n2-hardware-candidate`）。
5. **`spacemit_ime status=missing` 的语义已核实、无异常**（本轮一次自我证伪，如实记）：我一度怀疑它与 schema `status` 注文「missing status is interpreted as available」冲突，**查码后证伪该怀疑**——ODS 自称 status 的 single source of truth，`include/Weft/Dialect/Exec/IR/ExecOps.td:32-38` 明文：「a capability is available **only** when its status is exactly `available`；`unavailable`/`disabled`/`missing` are the distinct **unavailable** spellings」，实现于 `lib/Support/CapabilityModel.cpp:548-560 isUnavailableStatus()`。schema 的 `"default": "available"` 指的是 **status 字段缺省（absent）** 时的默认值，**不是**枚举成员 `"missing"`。故 `missing → unavailable`、`keys_evaluated` 回读 `unavailable` **是正确行为，无冲突、无 PENDING**。
6. **C1 腿的 69 files 是 F-1 检查器自报的核心域计数**，域由 `schema/family-regex.v1.json` 钉；本轮**未改该 manifest**。（注：manifest `$meta.head_status` 仍写 61 files @1bb06375，与当前 69 是核心域随代码长大所致，非本轮改动。）
