# 插件协议

**本文是可复制扩展接入协议的实体**：一个新 construction family 如何在**不改写 core
pass、不把 metadata 变成可执行 authority** 的前提下接入 Weft。当前可编译参照是
Weft-RV；future GPU 必须复用同一 construction contract，而不是加入 current EmitC
emitter 表。

读法口径见 [本层 index](./index.md#读法口径落笔前必读--四条)。硬规则全文住 [canon · 核心不变量](../canon/核心不变量.md)。各家族的具体边界见 [家族现状](./家族现状.md)。

---

## 【定法】Standard Flow

```text
canonical operator problem P=(S,g,ω)
  -> typed target/profile binding (f,c_f)
  -> catalogued family-local formula/construction
  -> legality + optional bounded selection
  -> selected weft.exec variant
  -> typed extension-family body or selected boundary
  -> optional plugin selected-body realization
  -> family artifact driver
       -> current optional WEFTEmitCLowerableRoute + common EmitC
       -> future family-specific artifact handoff
  -> target artifact packaging
  -> runtime/hardware evidence when claimed
```

For RVV, the typed body is low-level `weft_rvv` vector-level structure。Future GPU 必须构造
自己的 typed execution body；不得消费 RVV body 或 `flat_*` plan。

每个 production family 都必须进入公式/构造阶段。只有一个实现的 family 使用 deterministic single-candidate construction 与 honest-null 轴，不得直接从 source/variant 跳到 emitter。公式 catalog、覆盖与横向 cutover 见 [公式层与覆盖](./公式层与覆盖.md)。

problem、family binding、construction completion 与 artifact 的分层正本见
[执行问题与家族边界](./执行问题与家族边界.md)。

> 每家族的 build/maturity 状态住 tasks/journal，**不在本文**（见 [governance · 思维准则](../governance/思维准则.md#一主干纪律) §一 主干纪律）。

## [P-1] 接口冻结（准-ABI）【定法】

`ExtensionPlugin` 是**准-ABI**，不是内部便利面。其可序列化签名形态是一个进入 schema.def ⑤ 的声明式 schema 对象（[S-5]⑤，按 ID 引用；见 [能力模型 §[S-5]](./能力模型.md#定法s-5-schemadef-声明工件)，不在此复述）。因为它是准-ABI，**任何接口签名变更走 RFC**；纯附加式的变更记为 `extension not modification`（[F-2′] 操作门）。

经此冻结接口，一个插件可以贡献：

```text
fact + relation declarations
formula/construction descriptors + family-local typed evaluators
legality predicates
artifact patterns/handoffs (registered through the matching artifact class,
not open-coded into core)
artifact lowering hooks
tests
```

插件**不得为接入而编辑 core 目录下的任何文件**。需要 core 改动意味着：要么接口确实缺一条执行语义（经 RFC + I3 复核论证），要么这项工作放错了地方。

## 【现状】Hook 签名 —— 去哪找可编译形态

按 [P-1]，精确的可序列化签名声明一次（schema.def ⑤），C++ 接口**不逐句抄成散文**。但作者仍需知道**哪个 header、哪个类、覆写哪些虚函数**。

**权威源**：`include/Weft/Plugin/ExtensionPlugin.h`，类 `ExtensionPlugin`（**精确类型以该 header 为准**；下表只是发现索引）。family 插件实现的可覆写 `virtual llvm::Error …` hook：

```text
getName / getVersion / getCapabilities / registerDialects   identity, fact instances, dialect registration
constructFormulaPlans(FamilyConstructionRequest,
  FamilyConstructionResult)                                 artifact-neutral exact family construction result
supportsOperation / proposeVariants / collectVariantProposals  variant proposal
verifyVariantLegality                                        ② legality predicate
estimateVariantCost(VariantCostRequest&, VariantCostEstimate&)   selector cost hook（[SEL-1] 冷启动先验）
checkVariantEmissionReadiness / buildVariantEmissionPlan     emission planning
materializeSelectedLoweringBoundary / validateSelectedLoweringBoundary  selected-body realization boundary
configureTargetSupportExtensionBundle / registerTargetSupportTranslateRoutes  target-support wiring
```

【现状】`constructFormulaPlans` 的 base implementation fail closed；每个 live production
family 都显式实现 artifact-neutral construction，并为当前绑定 variant 返回 exact
`FamilyConstructionResult` typed operation/root 或 explicit unsupported。Target/profile 与
typed `c_f` 在调用该 lifecycle 前完成绑定。公共层只检查 result ownership/existence，不能
解释 family compute 或扫描 module 重发现 body。EmitC backend interface 不含 construction
hook；constructed-only artifact API 只机械降低 final body/plan，不得保留第二套
construction authority。

注册自由函数 `register<Fam>ExtensionPlugin(ExtensionPluginRegistry&)`（一个 `ExtensionPluginRegistrationFn`，声明在 family header）**与这些虚函数分开** —— 它是内建目录所调用的东西（见下 §注册）。

## 【定法】Registry Rules

registry 只拥有查找与编排：

- plugin registration;
- typed target/family applicability binding;
- capability/provider lookup;
- dialect and interface registration;
- variant builder lookup;
- legality hook lookup;
- selected-body realization hook lookup;
- artifact projection/driver lookup;
- optional diagnostic mirror collection.

registry **不得**从 plugin 名、family 名、route id、manifest、semantic role graph、source-front-door 标记、artifact metadata 或 descriptor 派生计算。Family binding 只建立 typed
construction owner 与 capability projection，不选择 candidate/leaf，也不由 artifact kind
反向确定 family。

## 【定法】Required Plugin Interfaces

### Formula / Construction

每个拥有 production operator/conversion/direct-route entry 的 plugin，都必须为这些入口暴露
只读 formula/construction descriptor，并在 family-local C++/MLIR 中实现 artifact-neutral
typed construction。每个 entry 必须能说明 source/problem 的 `S/g/ω`、绑定的 `c_f` 与唯一
construction owner。没有 production entry 的测试、demo 或纯模板 plugin 的分母为零，不靠
目录名推断。

Formula construction 必须发生在 legality、selection 和 artifact route/emission 之前；它输出
candidate/plan/body 参数、resource requirements 和 analytic prior。Construction completion
不得以 `emitc.func` 或任何 artifact-specific op 定义。Deterministic family 仍注册
single-candidate construction。插件不得在 source builder、selected-body materializer、
artifact projection 或 emitter 中另存一份同义解析决定。

公共 descriptor/catalog 是整个 software stack 的共同扩展接口之一，但不增加新的“六件套”计数；它只保存 identity、owner、domain、依赖轴和 typed entry 的静态关联，是现有 construction protocol 与 legality/emission 交付物的可枚举入口。它不是动态求值服务、provider registry 或行为 dispatcher；core 不得按字符串 formula id 调用 untyped/`Any` evaluator，也不得引入大一统 `FormulaResult`。公式求值和结果消费保持在 family-local typed call graph 中。

### Capability And Proposal

Plugins may expose capability matching and variant proposal hooks. Proposed variants must carry structured capability requirements and origin plugin identity. Capability facts constrain legality/realization; they do not create RVV dtype/config/body/route identities.

### Legality

Plugin legality owns extension-specific validation. Core checks generic structure, symbol resolution, capability presence, dispatch/fallback shape, and fallback coherence. Core does not hard-code RVV/IME/offload legality.

Legality 只裁剪 formula 已构造的候选，不补造 candidate、mechanism 或 `θ`。

### Selected-Body Realization

`realizeSelectedVariantBody` or an equivalent hook is a transient C++ compiler operation:

```text
selected pre-realized extension body
  + target capability
  + runtime SSA / ABI values
  + optional hints / policy / profile
    -> realized selected extension body
```

For RVV, any hint/config/profile fact that affects generated code must be consumed into concrete `weft_rvv` body structure before route construction.

`VariantSelectedBodyRealizationResult::isRealized` and similar booleans are transient C++ result codes. They are not persisted IR readiness states, dashboards, artifact ledgers, or progress markers.

### Artifact Driver / Optional Route Projection

The origin plugin owns artifact handoff construction:

```text
selected typed/realized body
  -> family artifact driver
       -> optional WEFTEmitCLowerableRoute for current EmitC artifacts
       -> future typed GPU/other artifact handoff
```

For RVV, the family artifact driver maps the exact typed body, including already selected dtype,
SEW, LMUL, policy, operand form and memory form, to RVV intrinsic/backend representation. Common
EmitC never infers those decisions from source metadata。Future GPU
artifact code similarly may only lower a GPU final body; it cannot receive source metadata or RVV
execution IR and construct GPU compute there。

Artifact projection 也不得重新运行 formula 或在 format/capability/regime 上二次选择；所有
code-affecting 结构在 selected typed body 中已经确定。

这里的 optional route 是 current artifact 的机械 projection，不是 FormulaProvider、
PlanProvider、route authority 或 body factory。它只把 final typed/realized body 投影为
backend type、intrinsic spelling、
operand binding、header 与 ABI 交付物。类似地，接口名中的
`materializeSelectedLoweringBoundary` 与 common EmitC materializer 是既有机械 lowering
hook，不表示 selected-stamp/materializer 生命周期，也不得事后补写公式结果。

### Current EmitC Lowerable Interface

The common EmitC lowerable interface exposes only generic materialization shape for current
EmitC/native artifacts. It may carry provider-owned payloads, but it must not interpret extension
computation。它不是 future GPU construction 或所有 artifact 的必经接口。

### Compute Role Interface

`WEFTComputeOpInterface` or similar common interfaces expose generic role/provenance only. They must not let common code interpret computation semantics, infer dtype, choose intrinsics, or branch on concrete families.

## 【定法】Plugin Locality —— 插件化 ≠ 零工作

### 新变化写在哪里

| 变化 | 主要 owner | 不应修改 |
|---|---|---|
| 新 operator / format / layout fact | plugin-local source front door 与 typed `g` | core family-name dispatch、emitter format switch |
| 新 target capability | canonical capability model 与 family-local typed projection `c` | formula 内重解析 board/march、全局 target singleton |
| 新 mechanism | family dialect/support 中可复用的最小 typed primitive | 复制完整 format×board point body |
| 新 analytic formula | family-local formula module + 同源 catalog descriptor | global Formula IR、按 id 动态求值的 provider |
| 新静态 regime | bounded typed `ω`，仅在真实承重时加入 | 任意 context bag、runtime data profile |
| 新 empirical residual | governed measurement row/key 与 bounded selector | candidate construction、legality、compute parameter |
| 新 construction family | plugin-local problem projection/capability/mechanism/formula/body/artifact/ABI/toolchain | core/common family branch、复用 RVV body 或把 GPU 塞进 EmitC emitter |

新增项只改自己的 typed owner 和必要 caller/test。若一次扩展必须在 formula、provider、
verifier 与 emitter 各复制同一知识，说明边界已经破坏，应先收回唯一 construction owner。

插件化**不**意味着新硬件零成本。

新增 IME / offload / future custom ISA/GPU 支持仍然需要：source/problem applicability；ops、
types、attributes；capability 定义；mechanism/formula；variant generator；legality/resource
rules；cost model；tuning rules；artifact lowering；runtime 或 toolchain adapter。这些是编译器
实现工作，属 C++/MLIR/TableGen/CMake，配 lit/FileCheck 与 C++ test（见 [实现栈](./实现栈.md)）。

插件化意味着：

- 新能力代码**集中在一个插件内**；
- core pass **不硬编码具体扩展名**；
- core pass 经 registry 与 interface 交互；
- high-level MLIR 语义转换**不为每个扩展重写**。

### Plugin-Owned

extension-specific 的：problem projection · capability · mechanisms/formula · types/ops ·
artifact lowering · tuning · runtime ABI · selected-body realization（当影响代码的
hints/config/profile 必须变成具体 body 结构时）· optional route projection · selected path 的
emission 诊断/镜像 · legality 细节 · toolchain workaround。

**Plugin-owned 不等于 Python-owned。** 插件的编译器行为仍是 C++/MLIR 实现。

### Core-Owned

canonical problem contract · capability registry · plugin registry · family binding/variant selection
编排 · dispatch/fallback 结构 · artifact-neutral ownership/diagnostic 编排 · 通用诊断格式。

Core 可经通用 interface 编排 selected-body realization 与 route-provider 调用，但语义仍 plugin-owned。Core **不得**代插件填 RVV/IME/offload 的 lowering pipeline、runtime ABI、artifact kind、intrinsic 名、dtype 选择或 supported-path 主张。

Emission-plan metadata 不是可执行 route authority。Core 只可在 selected-path 收集与 provider route 构造**之后**，把可选的 plugin-owned 镜像物化成 `weft.exec.diagnostic {reason = "emission_plan"}`。该物化仅限拷贝通用镜像字段与校验符号结构。它不是 lowering、runtime glue、artifact 生成、RVV 支持、正确性证据、性能证据或进度。

公共工具集成属前门/plugin-loader 职责，不是 core 的 target-family 分支。例如 `weft-opt` 可构造确定性的 `ExtensionPluginRegistry`、填入内建插件、注册插件 dialect、并把该 registry 传进依赖 registry 的 pass。共享 pass 逻辑仍须只经通用 `origin` 查找与插件 interface 路由。

### When Core May Change

系统**不得**承诺每个未来扩展都零 core 改动。

可接受的表述：

```text
If a new extension maps to existing capability, variant, resource, and emission interfaces, it should be added as a plugin.
If it introduces genuinely new execution semantics, the core interfaces may need extension.
```

可能需要扩展 core interface 的例子：分布式多 hart collective 语义；非标准一致性模型；device 侧调度队列；现有 dispatch/runtime 契约无法建模的异步副作用。

### Evaluation Metrics

对任何新插件，记录 core/pass 与 plugin-local 触碰、新 capability、ops/types、variant
builder、支持的 source/operator 类、selected-body construction、artifact driver/projection、
core 是否出现 extension-specific 分支，以及既有 variant/dispatch/artifact interface 是否被
复用。数量用于定位改动，不作为科研完成标准。

## [F-3] 变更收敛（Change Containment）【定法】

家族代码归拢到家族territory 后，一个家族接入 PR **收敛在：家族领地 + 表行 + docs + 共享注册行**：

```text
lib/{Dialect,Plugin,Target}/<Fam>/   problem projection, capability, formula, ops/types/attrs, legality, body, artifact/runtime
  + include/Weft/{Dialect,Plugin,Target}/<Fam>/  header mirrors
tables               capability fact rows + relation rows (schema/**) + ledger row
tests                test/**  ([P-2] 件 ④)
docs                 integration doc ([P-4])
registration         lib/Plugin/Builtin/BuiltinExtensionPlugins.cpp — 一行 kBuiltinExtensionBundles[]
                     (+ 当前出货 EmitC artifact 的家族：lib/Conversion/EmitC/Builtin/BuiltinBackendEmitters.cpp
                        一行 kBuiltinBackendEmitters[]；future non-EmitC family 使用其 artifact class 的注册点)
```

这是 [P-1] 的收敛形态（无 core dispatch/selection/lowering 编辑 —— 注册表行是唯一预期的共享触碰），也是接入五件套（[P-2]）的**空间对应物**。它**以家族代码确已归拢为结构前提**；家族代码仍散落之处，归拢它是**前置工作，不是把接入溢出进 core 的理由**。与零 family-name 分支（I3）及 [F-1] grep-clean 检查合起来，收敛是**泛化代价可审计的证据**。

### `Family-Onboarding:` trailer 与 [F-2′] schema-shape 冻结

一个需要进入现有 family manifest/regex 的接入可以编辑相应 `schema/**` 表行；只有当该
family 同时进入某个正式评价 roster 时才编辑对应 measurement/coverage 数据。当前
formula authority 与 production-entry coverage 来自 plugin registry/catalog 和真实
call graph，不要求为了接入写 `schema/coverage-sixstate.v1.json`。这些表行编辑不是对
冻结 schema *shape* 的编辑。该区分由 [F-2′] 门执行：

- **Marker**：接入 PR 由 `base..head` 中的 `Family-Onboarding:` commit trailer 识别（常量 `ONBOARDING_TRAILER`）。带 trailer 的 PR 按接入规则评级；不带的按 core-author *演进* PR 评级（RFC + `classify_schema_change`）。
- **规则 [F-2′]**：`is_f2prime_violation = is_onboarding AND (任一改动文件落在 schema.def 治理路径内)`。其*本意*是冻结 schema **shape**（`schema/capability.schema.v1.json` + 其 `VERSIONLOG.md`）：接入作者伸手进 schema.def——**哪怕只是加一个字段**——就是 falsifier 触发，**绝不以"附加式"为由放行**。接入必须经既有冻结 shape 集成，只加表行数据。
- **门的辖域 = `SCHEMA_DEF_PATHS`**（`capability.schema.v1.json` + `VERSIONLOG.md`），**不是整个 `schema/`** —— family 表行 schema（`family-manifest.v1.json` 等）是 [F-3] 工件，接入 PR 改它是**义务非违规**，不触 [F-2′]。RFC 版本日志见 `schema/VERSIONLOG.md`（extension-not-modification 体例）。
- **明确拒**：trailer 豁免（"PR 自我声明无害"）—— 那是未来绕门的正门。

> **【现状】门的实现与编排**：权威实现 = `.trellis/scripts/check_schema_gate.py`（`SCHEMA_DEF_PATHS` / `ONBOARDING_TRAILER` 均在其内）；它**有编排者** —— lit 测试 `test/Scripts/schema-def-f2prime-gate-redteam.test` 真调用其 `--self-test`。**本文只索引它，不重定义规则**（[P-1]）。
> 复核谓词：`grep -nE 'SCHEMA_DEF_PATHS|ONBOARDING_TRAILER' .trellis/scripts/check_schema_gate.py` · `ls test/Scripts/schema-def-f2prime-gate-redteam.test`

## [P-2] 接入五件套【定法】

一个家族接入是**一个 PR 系列**，五件**缺一不收**：

```text
① fact + relation table rows         (capability facts + implies/conflicts)
② legality predicate                 (plugin-owned, runs before artifact lowering)
③ construction + artifact pattern    (或一条显式的“复用既有 artifact class”声明)
④ tests                              (lit + family-appropriate artifact inspection/golden)
⑤ ledger entry                       (cost/attribution ledger row)
```

五件套是 [P-1] 的**逐家族具体形态**：每一件都经冻结的 family/plugin contract 流动，只触碰
family-local 面加表行（变更收敛 = [F-3]）。件 ④ 中，lit/FileCheck 证明编译器行为与 artifact
形态；面向目标的 artifact inspection/golden 由 family 决定——当前 RISC-V 使用 per-board
objdump，future GPU 应使用与 device artifact/toolchain 相符的检查。两者都不能替代真实
runtime/correctness/performance 证据（**编译≠硅封**，[L-6]③；I8）。

### ★ [P-2] 是**交付轴** —— 「五件套」的三个视图

「五件套」这个词在文档里被用在**三条不同的轴**上。**本 [P-2] 集（① 事实+关系 ② legality ③ 发射模式 ④ tests ⑤ ledger）是权威的*验收*定义** —— 它就是 PR 系列「缺一不收」的所指。另两个「五」**不是** [P-2] 的竞争定义；它们是同一次接入的*文件轴*与*仓库轴*视图。交叉映射：

| 轴 | 枚举 | Authority |
|---|---|---|
| **交付 / PR 系列（[P-2]，权威）** | ① 事实+关系行 · ② legality 谓词 · ③ construction+artifact 模式 · ④ tests · ⑤ ledger 行 | 本节（验收门） |
| **文件（逐家族）** —— 交付物落在哪 | ① `<Fam>ExtensionPlugin.cpp`（入口+事实）· ② `<Fam>VariantLegality.cpp` · ③ family construction + artifact driver · ④ `test/**` · ⑤ attribution/evidence | 一个*落地*视图，**不是第二个 [P-2]** |
| **仓库（整栈）** —— 五大件 / 6 components | schema · plugin-five-piece · front-door · selector · falsifier · measurement | 正交：整个模板，不是某一家族 |

交付件**不与文件一一对应**（③ 发射模式跨两个文件；⑤ ledger 是一行 `docs/` 表行，不是 `BackendEmissionDriver`）。文件轴的「五件套」指 `lib/Plugin/<Fam>/` 下的 5 个 `.cpp`；真实的链接触碰集**更宽**（见下 §真实触碰集）。

> ★ **「五」的消歧纪律**：模板级「五大件」与单家族级「五件套」**不是同一个「五」**，且前者口语称「五」实为 6 件。**禁再造第三个「五」**（见 [index §命名未决](./index.md#五已有既存所指--禁再造第三个)）。

### 【现状】Landing points —— 每件交付物实际住哪

`schema/*.json` shape 文件声明的是 *shape*，不是实例。具体的逐家族行/事实落在（**实核**）：

| 交付物 | 落点 | 备注 |
|---|---|---|
| ① capability **事实实例** | `lib/Plugin/<Fam>/<Fam>ExtensionPlugin.cpp` —— `getCapabilities()` 内 push 的 `PluginCapability(...)` | **C++，不是 schema JSON**。`schema/capability.schema.v1.json` 只是 aspirational shape（[GAP-P4-SCHEMA-DIVERGENCE]，见 [能力模型](./能力模型.md)） |
| ① relation 行（`implies`/`conflicts`） | 同一 `getCapabilities()` 数组 + capability-model 测试 | |
| formula/construction descriptor | `ExtensionPlugin::getFormulaCatalog()` 与 family-local formula catalog | 只读发现入口；typed evaluator/constructor 仍住 family-local code |
| ④ tests | `test/**`（lit + gtest） | [F-3] shared allowance |
| ⑤ C2 ledger 行 | `docs/method/C2_marginal_cost_ledger.md` | core LOC / plugin LOC / 新 caps / 新 ops（见上 §Evaluation Metrics）。**★该文件归档去向待裁**（`docs/` 树，见 [issues](../issues/index.md)），落点以裁定为准 |
| 历史评价 roster / 六态数据 | `schema/coverage-roster.v1.json`、`schema/coverage-sixstate.v1.json` | 仅兼容既有评价资产；不定义 formula coverage、authority 或 strong reconstruction |
| family 领地 + dispatch key | `schema/family-manifest.v1.json`（`source_ranges`）· `schema/family-regex.v1.json`（dispatch keys / core_scope）· `schema/family-dirs.v1.json`（C2-cost families） | [F-1]/[F-3]/[F-6] falsifier 行 |

这些 `schema/**` 编辑是**表行数据**（[F-3] 的"+ 表行"许可），不是对冻结 schema *shape* 的编辑。

## 注册（共享步骤）

一个家族**直到其 `register<Fam>ExtensionPlugin` 自由函数被录入内建目录，才变得可发现**。这是一次**对共享文件的真实编辑**，且**容易漏**——它不是五件交付物中的任何一件。

### 【定法】步骤

1. 在 family header 声明入口点：
   `llvm::Error register<Fam>ExtensionPlugin(ExtensionPluginRegistry &registry);`
   于 `include/Weft/Plugin/<Fam>/<Fam>ExtensionPlugin.h`（定义在 `<Fam>ExtensionPlugin.cpp`）。
2. 在 `lib/Plugin/Builtin/BuiltinExtensionPlugins.cpp` 加**两行**：一个 `#include "Weft/Plugin/<Fam>/<Fam>ExtensionPlugin.h"`，和 `kBuiltinExtensionBundles[]` 表内一行：
   `{"<fam>-extension-bundle", register<Fam>ExtensionPlugin},`。
3. **（当前仅针对 EmitC artifact class）第二个共享注册点。** 若 current family 出货自己的
   EmitC backend driver，则它还必须录入 `kBuiltinBackendEmitters[]`。这张表不是所有 future
   construction family 的总表；NVVM/ROCDL 等 non-EmitC artifact 使用相应 artifact class
   的注册与完成门。
   **现状 driver body**（可从 `TemplateBackendEmissionDriver.cpp` 发现）：
   `register<Fam>BackendEmitter` 构造 `TypedBackendEmissionDriver`；family plugin 已在 artifact
   API 之前完成 construction。Driver 只提供 type conversion、conversion target、lowering
   patterns、artifact cleanup 与 body-presence query，随后由
   `convertConstructedModuleWithBackendEmitter` 把 selected final body/plan 机械降成独立 EmitC
   module。它不能调用 formula、legality 或 selector，也不能成为 construction owner。
   注册本身：在 `lib/Conversion/EmitC/Builtin/BuiltinBackendEmitters.cpp` 加一个 `#include` 加 `kBuiltinBackendEmitters[]` 内一行（`::weft::plugin::<fam>::register<Fam>BackendEmitter,`），并在该目录 `CMakeLists.txt` 内加匹配的 `LINK_LIBS Weft<Fam>BackendEmitter` 行。
   **复用**共享 EmitC materializer、不注册自有 driver 的家族不触此文件；future non-EmitC
   family 也不触此文件。

> **【现状】两张表的实核表体**：
> `awk '/kBuiltinExtensionBundles\[\] = \{/,/^\};/' lib/Plugin/Builtin/BuiltinExtensionPlugins.cpp` → **8 项**（全部家族）
> `awk '/kBuiltinBackendEmitters\[\] = \{/,/^\};/' lib/Conversion/EmitC/Builtin/BuiltinBackendEmitters.cpp` → **7 项**（RVV / Demo / Toy / Template / TensorExtLite / IME / Scalar；**无** Offload）
> 家族册与三根表见 [家族现状](./家族现状.md#现状家族册)。

### 【定法】与 [F-3] 无-core-编辑的调和

两个共享注册文件都住在 `Builtin` `core_subdir` 下、不在 family 目录内，故按 `schema/family-manifest.v1.json` 的定义两者都是 **core-source**：

- `lib/Plugin/Builtin/BuiltinExtensionPlugins.cpp` —— 插件发现目录（`kBuiltinExtensionBundles[]`，每个家族）；
- `lib/Conversion/EmitC/Builtin/BuiltinBackendEmitters.cpp` —— 后端发射器目录（`kBuiltinBackendEmitters[]`，仅自带后端的家族）。

两点化解此张力：

- **两者都不是 I3/[F-1] 零分支违例。** `kBuiltinExtensionBundles[]` 与 `kBuiltinBackendEmitters[]` 是统一的注册*表*（family 名 / bundle-id 作字符串字面量或函数指针，用 `for` 循环遍历，**无 `if`/`switch` 判 family 名**）。`schema/family-regex.v1.json` 的 `core_scope` 已把 `BuiltinBackendEmitters.cpp` 祝福为"INTENTIONALLY in scope … zero-core-branch backend registration table"（声明的假阳性类），而 `BuiltinExtensionPlugins.cpp` 的表结构上同构。**向一张 family-agnostic 的注册表加一行数据，是 [F-3] "+ 表行"的精神，不是 core dispatch 编辑。**
- **两条许可都已在 manifest 内声明。** `schema/family-manifest.v1.json` 的 `shared_allowances` 携带 `plugin_registration` → `BuiltinExtensionPlugins.cpp` **与** `backend_emitter_registration` → `BuiltinBackendEmitters.cpp`，并列于 `table_rows` / `tests` / `docs` / `build_and_tooling` 之侧。家族 PR 触碰任一注册表行（以及自带后端家族配套的 `BuiltinBackendEmitters` `CMakeLists` `LINK_LIBS` 行）是**已声明、预期内的例外**，不是收敛违例。
- **checker 语义**：[F-3] checker 的 `evaluate_diff` **读 `shared_allowances`**（经 `registration_allowance_files`）：它解析 `$meta.containment_scope.shared_allowances` 并放行**具名的精确路径**注册文件（跳过 note/glob；构造上收窄）。故两个注册文件是**机检放行**，而非仅靠 reviewer 放行。护栏：具名指针禁通配符、只缩棘轮成立、反向测试在册。

> **【现状】checker 实存与编排**：
> - checker **存在，住 `tools/gates/check_family_locality.py`**（`registration_allowance_files` / `evaluate_diff` / `shared_allowances` 消费均在其内）。
>   ★ **路径已迁**：spec 前版称其住 `tools/lint/`，**该路径下无此文件**。
> - manifest 的 `shared_allowances` 实核含 `plugin_registration` 与 `backend_emitter_registration`（连同 `note` / `table_rows` / `docs` / `tests` / `build_and_tooling`）。
>
> **【目标】该门的 CI 编排**：**今日无编排者** —— `.github/` **不存在**（其下 workflow 已入 git-ignored 的 `_attic/`），全仓无第二个调用者。⟹ **"CI 常绿"不是现状**；判据在、脚本在、**自动编排缺席**。

## 【现状】真实触碰集（参照家族 = `Template/`）

参照 family 的文件布局只用于帮助开发者找到 owner，不是固定文件数、接入配额或科研证据。
当前 Template 体现的是下列职责分离：

```text
lib/Plugin/<Fam>/
  <Fam>ExtensionPlugin.cpp          proposal/cost + family construction entry
  <Fam>VariantLegality.cpp          family-local legality
  <Fam>FamilyContract.cpp           legality declaration + pure artifact ABI/callee constants
  <Fam>BackendEmissionDriver.cpp    mechanical current-artifact lowering
include/Weft/Plugin/<Fam>/          matching public family headers
lib/Dialect/<Fam>/ + include/...    family-local typed final body/plan
lib/Target/<Fam>/                   artifact bundle/ABI/runtime handoff
```

旧的 `<Fam>ConstructionProtocol`、`<Fam>EmitCRouteProvider`、construction manifest、
typed-role replay 和 metadata-only lowering boundary 不再是 family 模板。新增 family 可以按
真实职责拆分更多或更少文件；关键门是 construction 返回 exact typed result、artifact 只机械
消费、common/core 不出现 family-name compute branch。

接入仍需更新必要的 family-local CMake 与共享注册表行；这些 build-wiring 触碰不等于
construction 或 compute 住在 common。Future non-EmitC family 应注册到自己的 artifact
class，而不是为了复用现有表而伪装成 EmitC backend。

## 【定法】Required Plugin Sections（家族模板）

本模板是加入一个未来 extension family 的紧凑清单。它**不是**可执行 manifest 系统、semantic role graph 引擎、construction template 工件流水线、readiness dashboard 或 source-front-door 默认。

### 1. Family Identity

```text
family name
concrete MLIR namespace
plugin name/version
target capability ids
toolchain/runtime assumptions
maturity status (real / not yet built)
```

同时声明 canonical problem applicability、target/profile binding 与 family capability
projection。Family identity 不能由 artifact kind 或 route id 反推。

### 2. Capability Contract

定义结构化的 capability id、properties、relations 与 unavailable 诊断。Capability 事实约束 legality/realization；它们**不**创造 route id、dtype authority 或 artifact path。

### 3. Typed Body / Boundary

定义插件消费的 typed extension-family body 或 selected boundary。body 必须拥有 extension 的 compute/config/control/dataflow。RVV 的范例面：

```text
!weft_rvv.vector<elem = i32, lmul = m1>
weft_rvv.setvl
weft_rvv.load
weft_rvv.binary {kind = add}
weft_rvv.store
```

避免把 `rvv-finite-binary` 或 `weft_rvv.i32_*` 这类有限 dtype 前缀命名空间当架构模板。

### 4. Legality

陈述 plugin-owned legality 规则与通用 core 前提。Core 可检查通用结构与 capability 在场；extension legality 留在插件内。

### 5. Selected-Body Realization

若 hints/config/profile 影响生成代码，加一个 plugin-local realization hook：

```text
selected pre-realized body
  + target capability
  + runtime SSA / ABI values
  + hints / policy / profile
    -> realized selected body
```

**不要**把它持久化成 readiness 状态机。

### 6. Artifact Driver / Optional Route Projection

从合法的 typed/realized body 建 family artifact handoff。Current EmitC family 可以机械投影
`WEFTEmitCLowerableRoute`；future non-EmitC family 使用自己的 typed artifact handoff。任何
artifact driver 都不发明 extension 语义。

### 7. Runtime / Artifact Evidence

定义 runtime / correctness / performance 主张何时需要硬件或 runtime 证据（I8）。

### 8. Tests

把测试挂在生产路径改动上：lit/FileCheck 覆盖语法/验证/pass 行为/诊断；C++ test 覆盖 registry/provider API；negative test 覆盖 metadata-only / source-front-door / legacy-route authority；做 runtime/correctness/performance 主张时配 runtime 证据。

## [P-4] 外部可接入性【定法】

集成文档必须完备到**一个非 core 作者能仅凭文档完成一次家族接入** —— 这正是把"单次内部演示"升级为**可复制协议**的判据。"External-integrable"意味着接入五件套（[P-2]）、冻结接口（[P-1]）、typed-body/route 流（Standard Flow）与变更收敛规则（[F-3]）**各自都被写成可照做的程序**，而不是只能靠读 core 源码重建。

## 【定法】Source Front-Door Policy

source front door 的安全默认策略是 explicit-only 或 disabled：

```text
DefaultArtifactFrontDoorPolicy::ExplicitOnly
```

`DefaultArtifactFrontDoorPolicy::Eligible` **不是** RVV 工作的安全默认。广泛 eligible 的 source-front-door 策略只能由一个显式的未来任务使用，且须在成熟 typed-body route 已存在、且目标家族已证明 plugin-owned source 解释之后。

常设规则（source-front-door 路 fail closed，I7）：

- source-only RVV 标记默认 fail closed；
- source-artifact bundle 流水线不生成 positive RVV artifact；
- source-front-door metadata 不是 route / dtype / compute authority；
- source-front-door RVV 行为的测试是 negative/fail-closed 的，除非显式绑定到一条修正后的 typed-body route。

Toy / Template / TensorExtLite / IME / Offload / 未来插件的 source-front-door 场景是**未来示例**。它们**不得**变成当前默认工作流或取代 RVV 工作的模板。

## 【定法】Optional Manifests And Templates

Extension manifest、semantic role graph、construction template、示例 source-front-door 材料是**可选的规划/provenance 工件**。它们可以记录一个插件如何组织，但**不能**是可执行 source authority、route authority、dtype authority、artifact authority 或进度证明。

## 【定法】Emission-Plan Mirrors

插件 interface 可在 route 构造**之后**返回可选的诊断镜像。这些镜像可被序列化为 `weft.exec.diagnostic {reason = "emission_plan"}`。**它们不是 route 输入。**

允许的镜像字段：

```text
origin plugin
selected variant reference
lowering boundary reference
runtime ABI name
artifact kind/name mirror
required capability mirror
diagnostic result/reason
```

字段必须**镜像已做出的**插件决策。它们不得决定或恢复 route 支持。

## 【定法】Common Pass Names

用反映所有权的通用编排名：

```text
weft-select-variants
weft-realize-selected-bodies
weft-materialize-emitc-lowerable-routes
weft-lower-routes-to-emitc
weft-export-target-artifact
```

避免：

```text
weft-select-route
```

因为 route 构造是 plugin-owned，common/core 只编排 variant selection 与 route materialization。

## 【定法】Current RVV Fail-Closed Inventory

registry 与 artifact driver 在唯一 authority 是以下之一时必须 fail closed：

```text
RVVI32M1* route specs/slices
rvv-i32m1-* route ids
weft_rvv.i32_* helper namespace
!weft_rvv.i32m1 helper type
exact __riscv_*_i32m1 spelling
source-front-door marker
source-artifact bundle marker
descriptor residue
emission_plan status
artifact name/kind
manifest / semantic role graph / construction template
```

这些名字只能留在 negative test、deprecated inventory 或历史迁移注记中。

## Good / Bad Cases

Good (current EmitC family):

```text
core registry binds RVV and calls family construction/legality
-> RVV returns the exact final typed body
-> RVV artifact driver mechanically lowers that body
-> common EmitC materializes the typed artifact payload
```

Good:

```text
source-front-door RVV input
-> fail-closed diagnostic
-> no target artifact
```

Bad:

```text
DefaultArtifactFrontDoorPolicy::Eligible
-> positive RVV source-artifact route
```

Bad:

```text
Extension Manifest / semantic role graph
-> executable route construction
```

Bad:

```text
selected-path metadata
-> common lower-to-EmitC without an exact typed construction result
```

Bad:

```text
core branch recognizes RVV/Toy/TensorExtLite route id
```

Bad:

```text
VariantSelectedBodyRealizationResult::isRealized
-> persisted IR readiness state
```

## Tests Required

Interface 或 registry 改动需要聚焦测试：

- C++ tests for plugin lookup, exact construction-result handling, and artifact-driver dispatch;
- lit/FileCheck for generic diagnostics and fail-closed behavior visible in textual MLIR;
- negative RVV tests for legacy `RVVI32M1*`, `rvv-i32m1`, source-front-door, and metadata-only route inputs;
- positive tests only when they use corrected typed extension bodies and family-built artifact projections.
