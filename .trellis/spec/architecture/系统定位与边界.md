# 系统定位与边界

## 【定法】定位

Weft 是 high-level MLIR 之后的、可扩展 MLIR operator compiler / execution-layer software stack。

它接收已经确定的 operator、layout/format 与执行语义事实，依据 target capability 和 family-local executable knowledge 构造、选择并实现低层执行路径。RISC-V 量化推理是当前旗舰实现与主要压力域；RVV、GGML 或任一现有 format 不得进入 core/common 作为系统类别判定。

common abstraction 是：

> capability-scoped, typed extension execution

不是：

- 新 tensor/tile IR；
- 通用算法选择器；
- 每硬件一套孤立 backend；
- descriptor-driven code template；
- 通用 runtime autotuner。

旗舰负载域与论文评价范围见 [canon · 暂定科研主张](../canon/暂定-科研主张.md)。

## 【定法】主链

~~~text
MLIR operator / kernel-level input
  │
  ▼
plugin front door
  ├─ typed format/mechanism facts g
  ├─ bounded static context ω
  └─ canonical capability c
  │
  ▼
catalogued plugin-local formula / construction
  ├─ typed candidate or plan
  ├─ legality/resource bounds
  ├─ analytic prior
  └─ optional measurement key
  │
  ▼
bounded selector
  ├─ qualified measured winner if still legal
  └─ otherwise analytic prior / named fallback
  │
  ▼
selected typed extension body
  │
  ▼
plugin route provider
  │
  ▼
common EmitC / target artifact
  │
  ▼
real hardware evidence when runtime/correctness/performance is claimed
~~~

公式与 selector 的精确定义见 [变体流水线](./变体流水线.md)。
所有 production entry、公式 catalog 与覆盖要求见 [公式层与覆盖](./公式层与覆盖.md)。

## 【定法】g/c 解耦

“解耦”不表示 g 与 c 永不相遇。性能构造必须同时消费格式/机制事实和硬件能力。

正确边界：

- g、c、ω 来源、类型和 owner 分离；
- 在 catalogued plugin-local formula/construction 中首次受控汇合，随后由 legality、selector 和 typed stamping 消费其结果；
- typed plan/body 一旦产生，后续 emitter 不重新解析格式名、板名、march 或 measurement；
- 每个 decision 只消费所需 capability projection；
- 不建立全局 giant optional descriptor。

## 【定法】主要工位

| 工位 | 稳定职责 | 不得承担 |
|---|---|---|
| Facts/context | 格式、机制、layout、op/regime/必要 shape | board winner、intrinsic 模板 |
| Capability | ISA、VLEN/ELEN、SEW、vreg、IME tile、toolchain/runtime facts | format-specific compute |
| weft.exec | execution envelope、variant、requires、dispatch、fallback、ABI | selected family compute、dtype、schedule |
| Formula/construction | candidate/plan、mechanism 参数、resource requirement、legality 输入、prior | 输出 C/intrinsic 字符串、查 measurement winner |
| Selector | 在合法候选内选 winner，miss 时 prior/fallback | 创造 candidate 或绕过 legality |
| Typed body | 执行结构与已选参数 authority | 查 measurement、按板再选择 |
| Route/emitter | 机械实现 typed body | 重新决定 mechanism、LMUL、loop-order |
| Evidence | 验证正确性、部署与性能 | 反向定义 compute |

这些是职责，不要求一一对应独立目录或 class。

## 【现状】已存在的公式化资产

- RVVGearboxSchedule.h 作为 RVV closed-form/资源规则宿主；
- RVVFormulaDecision.h 已承载 Nibble、Codebook 与 repack accumulator-LMUL 三个
  机制专属 typed decision slice；
- Nibble、Codebook、KQuant、GridLookup、Ternary 五类 dequant plan；Nibble 与
  Codebook 已进入 typed decision，其中 Codebook 由 selected RVV capability 真驱动
  `{mf2,m1,m2}` 声明集的 legality/anchor（VLEN64/128/256 分别证成 m2/m1/mf2
  emission），并在 emission 前完整落印；四种固定 layout 由 construction 与 formula
  共用一张 canonical row；KQuant、GridLookup、Ternary 仍用 emission-period provider；
- direct/registry 的 selected RVV gate 已共用 canonical capability set、唯一 collector
  与 token predicate；不再容许 direct 路径本地扫描第一个 provider 或另解析列表；
- capability 对 VLEN、version、vreg_count 的真实消费；
- LMUL 已是 legality-bounded typed measured selection；SP4、loop-order 仍是局部
  measured selection；
- typed body 与 plugin route provider；
- winner hit、miss→prior、部分 feasibility revalidation 和 reason。

现状不能外推为：

- 所有 plan 字段都 analytic/c-driven；
- Codebook 的 bounded declared candidate set 覆盖未来所有 VLEN/LMUL，或已经给出
  全局最优 anchor；
- measurement 已单源；
- emitter 已完全机械；
- IME 达到 RVV 同等级公式与性能成熟度。

## 【目标】横向统一工程 contract

每个承重 decision 应能列出：

~~~text
decision id
typed g/c/ω inputs
candidate or typed plan
legality/resource verdict
analytic prior
consumed fields
reason/domain/fallback
optional measurement key
selected typed result
consumer
~~~

它由 family-local typed C++/MLIR evaluator 实现，并通过公共只读 catalog 枚举；不需要表达式 DSL。所有 current production operator entries 必须在同一次 horizontal rebase 中进入该 contract，不能保留“已迁公式”和“其余旧公式”两个世界。

## 【定法】一个统一系统

RVV、IME、Scalar、Offload 和 future vendor extension 是同一 Weft suite 内的 family：

- 共享 capability 语义、plugin lifecycle、core orchestration 和 measurement 规则；
- 保持 family-local facts、plans、legality 和 emitter；
- core 只经 interface/registry 调用；
- 每个 production family 都注册 formula/construction descriptor，并通过 typed evaluator 构造 body；
- 只抽 catalog、axis-use、result-kind 和 orchestration 等真正共同的最小 contract，不抽 family compute。

## 【定法】前端与后端边界

属于 execution-layer formula/realization：

- 固定 op+layout 下的 LMUL/SEW/VL policy；
- load/strip/unroll/accumulator/reduction layout；
- legality/resource pruning；
- family-local candidate selection。

不属于当前后端公式 novelty：

- 改写高层算法；
- 选择完全不同的模型/算子语义；
- 修改框架持久化权重布局；
- 图级融合和调度搜索。

## 【定法】runtime 边界

当前系统是 static/AOT construction 加 offline-qualified selection。

sparse、gather/scatter 或 MoE 的运行时数据分布若未来进入，必须先具备：

- typed observer；
- bounded profile；
- 预构造且静态合法的候选；
- observation/dispatch/switch 开销；
- 稳定策略与反抖动；
- 真实 workload 与归因。

缺少上述实现时，只能写 future，不得把 runtime 当当前第三层或缺失实验。

## 【定法】禁止结构

- core family-name branch；
- metadata/reason/artifact 反向定义 compute；
- measurement row 创造 route、dtype 或 mechanism；
- emitter 重做 selector 决定；
- Formula IR 或 giant optional plan；
- descriptor-driven computation；
- runtime profile 在当前热路径提前接线；
- 为覆盖率制造不被 consumer 使用的 g/c/θ。
- 某些 operator 走公式层、另一些 production operator 继续在 builder/emitter 隐式决定；
- catalog 只登记少数“代表公式”，其余 production analytic authority 不入分母。
