## 二、硬件条件与硬件证据探针

具体硬件环境（RVV main、IME、runtime-offload）是**当前事实、会变**；权威定义在 [architecture · 能力模型](../architecture/能力模型.md)「【定法】Target Profiles」，板身份钉死在 [measurement](../measurement/index.md) §3.1。本文件只留与**证据解释**相关的、durable 的部分。

**可复现的有界硬件 / 工具链证据** 由 `scripts/rvv_remote_probe.py` 采集，产物写在 `artifacts/tmp/rvv_probe/<run-id>/` 下，含脱敏命令日志 + 一份 JSON 摘要（uname/kernel、architecture、hart 数、clang/cmake 可用性、有界 RISC-V/vector CPU 提示、非交互 sudo 能力、以及最小手写 RVV intrinsic 的编译/运行结果）。该 JSON 还可含一段脱敏的 `capability_facts`，用于编译器侧的 profile 边界。

**这些事实的地位（严格）**：它们是**插件本地 C++ RVV capability profile 的输入**——由 profile 校验后填充 `TargetCapabilitySet`。它们**本身不是**编译器内部结构，**也不是** Weft-RV 发射出可执行 RVV 代码的证明。

⟹ 该探针是未来 RVV 编译器主张的**前置证据源**，**它自己不是** Weft-RV 的正确性 / 运行时 / 发射支持 / 性能工件。

## 三、研究问题（Q1–Q5）

> 用途：校准覆盖面与实验设计。**下列"对象"清单不使某条高层 lowering 路成为源权威**（见每条的硬约束）。

### Q1 · Weft-RV 能否在真 RVV 硬件上生成有效代码？

**对象**：`matmul` · batched matmul · `softmax` · layernorm / rmsnorm · rope · elementwise + reduction 融合 · attention micro-kernel 片段。

> **硬约束**：这些对象**校准 RVV 覆盖面与未来前端证明**，**不**使当前的高层 Linalg / 前端 lowering 成为源权威。当前 RVV codegen 主张仍须流经：选中的 `weft.exec` 变体 → typed `weft_rvv` body → RVV 插件合法性 / realization → provider route → 公共 EmitC。

**对照**：MLIR linalg/vector 默认 lowering · LLVM 自动向量化 · scalar/OpenMP 基线 · 手写 RVV kernel（若有）· 既有 AI-Benchmark RVV kernel（若可用）。

> **硬约束**：MLIR Linalg/Vector 默认 lowering **仅作对照 / 参考**，除非某个未来前端任务显式选择它。

**指标**：正确性 · 单线程性能 · 多线程性能 · 编译成功率 · 相对默认 lowering 的性能 · variant-local tuning 收益。

### Q2 · 能力模型是否真的参与 pass 决策？

**Profile**：RVV only · RVV + offload runtime · RVV + IME · fallback-only。

**期望行为**：

| Profile | 期望 |
|---|---|
| RVV only | RVV 变体 + fallback |
| RVV + offload | RVV 变体 + offload 变体 + dispatch + fallback |
| RVV + IME | RVV 变体 + IME 变体 + dispatch + fallback |
| fallback-only | fallback |

**指标**：生成的变体与能力相符 · 非法变体被 verifier 拒 · dispatch 条件正确 · 能力变化会改变 pass 决策 · 诊断清晰。

### Q3 · 扩展插件接入是否局部？

**参照流程**：系统已有成熟 RVV 插件 → 加 offload 插件 → 加 IME 插件 → 度量核心 pass 改动与插件边界。

**指标**：核心 pass 改动 LOC · 插件 LOC · 新增能力数 · 新增 op/type 数 · 新增变体生成器数 · 支持的高层算子数 · **核心 pass 内的扩展专属分支数** · 对 `weft.exec.variant` / dispatch / verifier 编排的复用度。

### Q4 · runtime-offload 能力能否接进同一执行层？

Q4 验证 **runtime-offload 能力接入**；offload route 在真生产者出现前**一律 fail closed**（[canon · 核心不变量](../canon/核心不变量.md) I7）。**它不得引入 source-front-door 或 offload 工件权威。**

**对象**：大 matmul · conv · transformer block 或 MLP block（若 runtime 支持）。

**对照**：RVV CPU 变体 · Sophgo offload 变体 · RVV + offload dispatch · fallback。

**指标**：offload 阈值 · 端到端延迟 · host-device 传输开销 · runtime 启动开销 · shape 大小对选择的影响 · fallback 正确性。

> **硬规则**：这验证的是 **runtime-offload 能力**，**不是** RISC-V 自定义 ISA。

### Q5 · 插件本地的矩阵扩展接入能否被展示（IME 第二家族）？

Q5 覆盖 **IME 插件本地的矩阵扩展接入**；IME 的 runtime / 性能主张需要**真 IME 硬件 / 工具链证据**（[canon · 核心不变量](../canon/核心不变量.md) I8）。

**对象**：matmul · batched matmul · attention qk/av block · MLP dense block · int8/fp16/bf16 dot-like kernel。

**对照**：RVV 变体 · IME 变体 · fallback · 手写或 vendor IME kernel（若有）。

**指标**：核心 pass 改动 LOC · IME 插件 LOC · IME 变体生成覆盖 · IME 合法性 verifier 有效性 · IME 发射成功率 · 适配 kernel 上相对 RVV 的性能。

## 五、基线纪律（**本节只列 CANON 未承载者**）

> 已在 CANON 的部分（scalar 非贡献基线 → [L-6]② · micro 且 e2e → [PERF-1]④ · 状态枚举与 stale 律 · Amdahl 传导会计 · 对手贴墙 parity = 满分）**不在此重抄**，见 [§一](#一禁副本指针表读本文件前先看)。

### 5.1 归因严谨（适用于**每一条结构性主张**，不是一个独立的 Win 类）

一个 pass / 结构的 ON-OFF 数字**不自动**是**结构性**赢。

若 ON 臂同时改变了**结构** *和* 一个附带的发射属性（例如它恰好避开了 OFF 臂的发射器碰巧引入的一次内存往返），则 ON/OFF 差值**把两者混为一谈**。

**要把赢归因给结构，必须**对照一个**同结构、但被称职发射的基线**做分解（例如：寄存器保留累加器的 per-iteration reduction）。

**若该同结构称职基线与 ON 臂打平 ⟹ 结构贡献 = NULL** —— 只许报 ON/OFF 数字连同它**真实但非结构性**的机制。

> **真实实例**：一个 deferred-vs-per-iteration reduction pass 显示出很大的 ON/OFF 差距，但一个寄存器保留的 per-iter 对照**与 deferred 臂打平** —— 差距全是 per-iter `out[0]` 的内存往返，**不是** reduction 结构延迟；结构新颖性**未被展示**。

### 5.2 新硬件单元 / build-swap 主张需要一个"**不可能有帮助**"的对照

当一个数字比较的是**两个分别构建的产物**（例如 IME-enabled lib vs non-IME lib），它把新单元与**两次构建之间的任何**全局工具链 / codegen 差异**混淆**了。

**必须**包含一个新单元**物理上不可能**贡献的**对照 regime**（例如对矩阵 / MAC 阵列而言的 M=1 内存带宽受限 decode）；**若"赢"在那里也出现 ⟹ 它是全局 codegen artifact，不是该单元。**

**干净的单元隔离要求同一工具链、只切换该单元**（例如同一编译器上 `SPACEMIT=ON` vs `OFF`），**不是**两个独立构建的库。

> **真实实例**：一个重建的 IME-enabled lib 显示出 "prefill" 加速，但在矩阵单元不可能帮忙的 M=1 decode 上也有相近加速 ⟹ 收益是全局 codegen、不是该单元；**单元隔离后的 e2e 赢仍为 NULL**。

### 5.3 repack / block-as-lane kernel 的性能主张

- **必须点名 VLEN regime**，且**必须**对比框架在**同一 VLEN** 上的**实际**基线（若它出货了手调的 VLEN-native kernel 就用那个，否则用它的通用 fallback）——**绝不用另一个 VLEN 的 kernel**。
- **repack 是否赢，由「对手强度 × 计算密度」决定，不由 repack 的 lane-shape 决定。** repack 只在同-VLEN fallback 是一个它能 out-stream 的**重**kernel 时才赢；对上一个**精简**的 fallback、或一个手调的 VLEN-native kernel，它**输**。
- 此时 tune **应当 DECLINE 它**（选 fallback = 匹配框架自己的算法）。**DECLINE = 匹配框架 = 避损，不是贡献。**
- repack-vs-fallback 的选择是**算法 / 布局选择（前端 / 库）**，**不是**对固定 op+layout 的能力驱动 lowering（后端面）；前后端判别器见 [architecture/system-positioning](../architecture/系统定位与边界.md)。**它不是 kernel bug，也不是一条 speedup 主张。**

> **真实实例**：同一个 repack、在同一个固定且正确的 lane-shape 下，**赢**了一个重的同-VLEN fallback，却**输**给一个精简的、以及一个手调的 VLEN-native kernel —— 决定结果的是**对手强度**，不是 lane-shape。

### 5.4 发射物的"真被用上"必须被证明

性能主张须有真 `ssh` 硬件证据、绑具名 profile（I8）；**被发射的 kernel 确实被调用**须被证明（ENGAGED 标记 / **最终装机二进制**的 objdump），**不得假定**。

## Forbidden Interpretations

**Do not claim**（原样保留）：

```text
Sophgo offload is RISC-V custom ISA extension.
Ordinary tile-size tuning is the main theory.
A vector-vs-scalar speedup is an N3 tune contribution.
A microbench win is an end-to-end win without an e2e measurement.
A pass-ON/OFF speedup is a structural-transform contribution without a same-structure competently-emitted control.
A build-swap speedup (e.g. IME-lib vs non-IME-lib) isolates the new hardware unit without a can't-possibly-help control regime.
AME is current verified primary hardware.
Any future extension never needs core changes.
Weft-RV is a new high-level tensor IR.
Structured kernel validation objects are current source-route authority.
Offload or IME dispatch is required before RVV typed-route maturity.
Source-front-door generated artifacts prove RVV maturity.
```

**Use**（原样保留）：

```text
Sophgo offload is runtime-offload capability.
Tuning is a system ability inside capability-aware variant selection.
Current mainline is RVV; later IME validates new extension plugin integration.
Extensions that map to existing interfaces support plugin-local integration.
Weft-RV is a RISC-V execution layer after high-level MLIR.
```
