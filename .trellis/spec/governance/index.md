# Governance Specs

本层回答：如何在用户给定范围内可靠推进、什么时候需要计划或 task、什么时候必须请求用户决策，以及如何维护 spec、issues 和证据。

> **版本**：v8
> **核心裁决**：Trellis 是可选的项目记忆与规划工具，不是 GPT 开工许可系统。用户的当前请求定义工作范围；spec 提供稳定约束；task 只在能降低复杂度、并行冲突或实验漂移时使用。

## 权威顺序

1. 用户当前明确指令与范围。
2. 安全、权限和不可逆操作边界。
3. 当前代码、测试、工具与实验工件所证明的事实。
4. canon 与 architecture 中的稳定契约。
5. issues 中的已知问题与边界。
6. task、旧计划、简报和历史记录。

旧 task、旧 goal 或旧简报不得覆盖新的用户范围，也不得把已完成事实重新写成缺口。

## Pre-Development Checklist

- [ ] 当前请求授权了什么修改？哪些目录和外部动作不在范围内？
- [ ] 已读根 spec、相关 layer 和当前代码事实吗？
- [ ] 是可逆、局部的正常实现步骤，还是会改变科研定义、公共接口、外部系统或历史数据？
- [ ] 是否存在用户改动或并行写入？存在时是否精确控制 touch set？
- [ ] 这一步推进柱一、柱二、工程正确性或代表性性能中的哪一项？
- [ ] task 是否能显著帮助多阶段工作、并行协作或实验预注册？若不能，不必创建。
- [ ] 需要测量时，实验问题、候选、重复数、正确性和落点是否已预注册？预注册不要求绑定 Trellis task。
- [ ] 将要写入的规则是否已经有唯一住址？有则更新原处并链接，不复制。
- [ ] 当前数字是否来自可复跑工具或主表，而不是旧文档转抄？

## 推荐上岗顺序

最小阅读集合：

1. 根 README；
2. [spec 根地图](../index.md)；
3. [canon](../canon/index.md) 的核心不变量与非目标；
4. 与当前修改相关的 architecture、measurement 或 evidence 文件；
5. 需要查既有问题时再读 [issues](../issues/index.md)。

无需为了简单、明确、可逆的修改遍历全部 task 历史，也无需初始化“开发者身份”。

## task 何时有价值

推荐创建 task：

- 多阶段、跨多日或需要恢复上下文；
- 多 agent/多 worktree 并行；
- 跨层接口或大范围重构；
- 正式实验 campaign，需要固定问题、候选、重复数和判据；
- 用户要求保留任务树记录。

通常不需要 task：

- 用户直接要求的单阶段文档或 spec 修正；
- 小型、可逆、触碰集明确的代码修改；
- 只读诊断；
- 已有计划已经足够表达依赖关系。

task 是计划和记录，不是修改代码或运行测试的授权来源。

## Quality Check

- 用户当前范围没有被旧 task 扩张或缩窄。
- spec 描述稳定契约，当前进度和数字留在代码、主表、ledger 或 issue。
- task 的存在与否不影响实现合法性；需要 task 时，它确实降低了协调成本。
- 没有“队列永远非空”“必须持续续队首”或“只有检查点才能停”等强制代理行为。
- 并行只在确有独立工作且 touch set 不相交时使用；单线工作无需证明自己为何没有并行。
- 任何重大定义变化都有用户明确裁决；本轮两柱、六律、公式核心和 Trellis 可选化即属已明确裁决。
