# 思维准则 —— 开发与审查前的检查清单

**这不是门禁，是判断依据。** 条文本体住各层 spec；本文件只给「动手前先问自己什么」。
**guide 与具体 spec 冲突，以具体 spec 为准。**

---

## 一、主干纪律

### 主要标尺

每项工作至少推进以下一项：

- **柱一**：能力驱动、类型化、可复用的 execution-layer 扩展模板；
- **柱二**：把高性能知识变成公式构造、合法域、有界选择和机械 realization；
- **工程地基**：正确性、覆盖、可复跑性、spec/code 一致性；
- **真实性能**：deployed ggml、代表性强对手或端到端传导。

两柱、六律和贡献组织的当前提案见 [canon · 暂定科研主张](../canon/暂定-科研主张.md)。任务不必为了“看起来像论文”而存在，但也不应沉迷于不改变系统能力的 closeout。

### 进度怎么量

进度按多维事实判断：公式/decision authority、capability 完整度、typed construction、measurement 单源、跨 extension 复用、deployed 性能、强对手成色和 e2e 传导。不要压成 task 数、commit 数或单一论文完成百分比。

### 主干 vs 枝节

- **主干** = 维护完整 operator compiler；收拢散落的 g/c/ω construction authority；
  横向消除 provider/verifier/emitter 的公式重放；让现有 leaf 逐步达到 strong
  reconstruction；继续 capability transfer、deployed/strong-opponent/e2e 性能。
- **枝节** = adjacent route seam、又一个 ABI/artifact evidence closeout、rename/ownership 重排、metadata-only round、把一个算子拆成 N 个 boundary/owner/contract task。
- **主干难、枝节易；loop 的天然引力往枝节滑。默认抵抗这个引力。**

### 反模式（点名）

- **微缝拆分**：把同一次 authority 重构拆成多个 boundary/provider/owner/contract/closure
  task，留下可合入双轨。横向公式层以完整 production domain 为一个工作单元；普通局部
  修改则无需为了 Trellis 人为创建 task。
- **无限证据 closeout**：route family 已 production-validated 后还在它上面反复刷 artifact/ABI/ssh 证据。**验证过一次就停。**
- **gate 反复重开**：给同一处反复加 attr/fact 再「关闭」。**这说明当初的拆分是假的。**
- **挑小而安全**：回避难的主干问题（strong reconstruction、真实 capability 因果、
  真打赢代表性框架出厂 kernel），去做容易出「完成」感的小修。

### 取舍（不是 checklist）

- 一个诚实的难主干步 **>** 五个容易的 closeout。
- 同一 family 第二次 evidence closeout 之前，先问：是不是该去推 formula 因果、
  reconstruction / capability transfer / 实测胜出了？
- 公式 authority 重构优先横向完整，不能用一个纵向样板替代全项目 cutover；进入
  strong reconstruction 或性能实验后，再把代表性实例打穿到真能构造、真能跑且能比较。
- 宁可一个 task 大一点、真推进主干，也不要十个小 task 原地打转。

### 停止和换向

- route family 一旦 production-validated：停止在它上面加证据/seam，记录结论，转最近的主干缺口。
- 发现自己在写第 N 个同模板的 contract/owner/closeout：停下，问「这是枝节吗？」——**大概率是。**
- 当前用户请求已经完成或需要新的重大选择时，可以交付或请求方向；无需为了保持队列非空继续生成工作。

## 二、能力优先设计

新增 target feature / variant 生成 / legality 检查 / dispatch / tuning / emission 逻辑前用。

### Checklist

- [ ] 建模的是哪种 target 事实：ISA、uarch、runtime/offload、toolchain、memory、还是 thread runtime？
- [ ] 这个事实表示在 `#weft.target` / `#weft.ext` / `#weft.accel` 或等价的结构化对象里的什么位置？
- [ ] **哪个 pass 决策**因为这个 capability 的存在或缺席而改变？
- [ ] variant 在 `requires` 里声明这个 capability 了吗？
- [ ] 缺席由 verifier failure、runtime dispatch、还是 fallback 处理？
- [ ] 诊断信息说清了「缺哪个 capability」和「哪条 emission/runtime 路径不可用」吗？
- [ ] 扩展专属检查都委派给 plugin verifier 了吗？
- [ ] 硬件/profile 事实**只**用于约束 plugin legality/realization，没有用来定义 RVV dtype/config/route 吧？
- [ ] RVV 的 dtype、config、operation kind 是 typed `weft_rvv` body 里的**结构**，或已被消费进 realized body 吗？

### Red Flags

- Capability 只以注释或字符串 metadata 形式存在。
- Core pass 直接按具体扩展名分支。
- 必需的 toolchain/runtime 缺席时 variant 仍能走到 emission。
- Fallback 只存在于散文里，不在 IR/metadata 里。
- VLEN / dtype 支持 / runtime 可用性等 profile 事实靠**猜**。
- 用 capability/profile 事实去发明 route id、artifact 名、intrinsic 拼写，或当 RVV dtype authority。

> 条文本体：[architecture](../architecture/index.md) I1 / I3 / I5、[canon](../canon/index.md) §九（S-\*）。

## 三、复用优先

写新代码前用。**重复代码是不一致性 bug 的第一来源**：修了 bug 不传播、行为逐渐分叉。

### 先查再写

```bash
grep -r "functionName" .    # 相似函数名
grep -r "keyword" .         # 相似逻辑
```

| 问题 | 若是 |
|---|---|
| 已有相似函数？ | 用它或扩展它 |
| 这个模式别处用过？ | 跟随既有模式 |
| 这该是共享工具？ | 建在正确的位置 |
| 我在从另一个文件抄代码？ | **停** —— 抽成共享 |

### 何时抽象

- **抽象当**：同样代码出现 3+ 次 · 逻辑复杂到会有 bug · 多方都需要。
- **别抽象当**：只用一次 · 平凡单行 · 抽象比重复更复杂。

### ★不对称机制产出同一结果 = 静默漂移

两个不同机制必须产出同一文件集时（如 init 走递归目录拷贝、update 走手写 `files.set()`），**结构性变更只沿自动机制传播，手写的那个静默漂移**。症状：init 完美，update 建到错路径或漏文件。

- [ ] 迁移目录结构时，搜出**所有**引用旧结构的代码路径。
- [ ] 一条自动派生（glob/copy）+ 一条手工列举 ⟹ **手工那条必须同步更新**。
- [ ] 加回归测试比对两个机制的输出。

### 批量修改后

1. **复查**：所有实例都改到了？ 2. **搜索**：grep 找漏网。 3. **考虑**：这该抽象吗？

## 四、跨层数据流

**大多数 bug 发生在层边界，不在层内部。**

### 动手前

1. **画数据流**：`Source → Transform → Store → Retrieve → Transform → Display`。每个箭头问：数据是什么格式？会出什么错？谁负责校验？
2. **认边界**：API↔Service（类型不匹配、缺字段）· Service↔DB（格式转换、null）· Backend↔Frontend（序列化、日期）· Component↔Component（props 形状变更）。
3. **定契约**：每个边界的精确输入格式、精确输出格式、可能的错误。

### 常见错误

- **隐式格式假设** → 边界处显式转换。
- **散落校验**（多层校验同一件事）→ 入口处校验一次。
- **抽象泄漏**（组件知道数据库 schema）→ 每层只认识邻居。

### Checklist

- 实现前：[ ] 完整数据流已画 [ ] 所有层边界已认 [ ] 每个边界的格式已定 [ ] 校验位置已决。
- 实现后：[ ] 边界情况（null/空/非法）已测 [ ] 每个边界的错误处理已验 [ ] 数据往返不丢。

## 五、计算边界审查

新增任何 op / dialect / lowering pass 前用。

### Checklist

- [ ] 这个新构造**组织执行**，还是**表达算法语义**？
- [ ] 若是算法语义：为什么它没被 Weft-RV 之前的 high-level MLIR 表示？
- [ ] 若是硬件执行行为：哪个 WEFT extension family 拥有它？
- [ ] `weft.exec` 是否只含 kernel / target / capability / variant / requires / region / hart_parallel / mem_window / runtime_param / dispatch / fallback / diagnostics 结构？（[architecture](../architecture/index.md) I2）
- [ ] matmul / softmax / reduce 语义是否**不在** core dialect？
- [ ] 这个构造保住了 plugin-driven variant proposal 吗？
- [ ] 当前 RVV 工作里，路径是否起自 hand-authored/selected Weft-RV MLIR + typed `weft_rvv` body，**而非新的 high-level frontend**？
- [ ] selected body 是否显式 import/consume `mem_window` / `runtime_param` 的 ABI 值？
- [ ] 若 performance config 影响代码，它是否被消费进 **realized body 结构**，而非 status metadata？

### Core 内允许

```text
weft.exec.kernel
weft.exec.target / target attachment
weft.exec.variant
weft.exec.requires
weft.exec.hart_parallel
weft.exec.region
weft.exec.mem_window
weft.exec.runtime_param
weft.exec.dispatch
weft.exec.fallback
weft.exec.diagnostic / diagnostic metadata
target/capability/cost/tuning/dispatch metadata
```

### 属于 extension family

```text
RVV vector register ops
IME fragment/mma/dot ops
offload buffer/runtime call ops
future custom instruction ops
future vendor runtime ops
```

### Core 内禁止形态

```text
weft.matmul
weft.softmax
weft.generic_reduce
weft.generic_tile
weft.generic_mma
high-level tensor compute in core dialect
```

### 正确的 transform 形状

当前 RVV 形状：

```text
canonical operator problem P=(S,g,ω)
  -> target/profile binds RVV + c_rvv
  -> RVV formula / legality / optional bounded selection
  -> exact typed low-level weft_rvv body + final plan
  -> RVV artifact driver mechanically lowers exact body
  -> common EmitC legalization / target artifact
```

未来 frontend 形状（**尚未建**）：

```text
typed source adapter / canonical operator problem
  -> target/profile binds a construction family
  -> family-local construction produces its exact typed body
  -> family artifact driver lowers through its own artifact class
```

## 六、插件局部性审查

新增或审查 extension plugin 前用。

### Checklist

- [ ] 这个 plugin 提供什么 capability？
- [ ] 它注册什么 dialect / ops / types / attrs？
- [ ] 它能为哪些 high-level op 类提 variant？
- [ ] 哪些 legality 规则归 plugin 所有？
- [ ] 哪些 tuning 参数与 cost 输入归 plugin 所有？
- [ ] 哪条 emission/runtime/toolchain 路径归 plugin 所有？
- [ ] 当 performance/config 需要具体 body 结构时，plugin 是否拥有 selected-body realization（如 `realizeSelectedVariantBody`）？
- [ ] plugin 是否拥有 exact typed body 到扩展专属 type/intrinsic/ABI/artifact 的机械映射？
- [ ] 它用了哪些 core API？
- [ ] **有没有哪个 core pass 因此长出了扩展专属分支？**
- [ ] 若 core 改了：改的是**通用 interface 扩展**，还是**具体扩展的 workaround**？

### 局部性证据（评估接入时记录）

记录真正的局部性变化：core/common 是否新增 family-name compute branch；新增 capability、
mechanism/formula、typed body、legality、artifact driver 与 tests 分别落在哪个 family owner；
共享 lifecycle/registry/interface 是否原样复用。不要用固定 LOC 配额、provider 复用率或
manifest 字段数替代代码所有权判断。

### Red Flags

- core 编排代码里出现 `if hasRVV` / `if hasIME` / `if hasSophgo`。
- 新扩展的 lowering 住在 plugin adapter 之外。
- 未来扩展为图方便被塞进 RVV 或 IME dialect。
- 把 pluginization 说成「零工作量硬件支持」。
- common/core 代码去选 RVV 调度、intrinsic 名、C vector 类型、dtype 或 route id。
- 把 emission-plan/status/artifact metadata 当 construction 或 artifact authority。

> 局部性证据、模块化成本与现有工件见 [evidence](../evidence/index.md)；条文本体见 [architecture](../architecture/index.md) I3 / I4 与 [canon · 核心不变量](../canon/核心不变量.md)。

## 七、去死镜像（删死码）

RVV family 的「字符串机器」夹着大量 metadata-mirror / route-validation 脚手架；它们和**活的发射器**同名前缀、同文件、逐行交错。**删错一个就截肢了真链路。**

### 先分清：活发射器 vs 死镜像（命名前缀陷阱）

| 形态 | 判定 | 处置 |
|---|---|---|
| `get*RouteFacts` / `add*RouteFamilyMetadataMirrors` / `materialize*` / `build*` 真 EmitC ops | 构造**真 IR / 真产物**，在 export 路径上有活 caller | **保留**（I5 typed body / I8 产物） |
| `get*/build*RouteValidationContract`、`get*RouteMetadataMirrorContract[Set]`、`append*Validation*`、`*RouteValidationKind` | 把发射器输出**再拼一遍**对镜像做等值断言 | **删除**（I4 病灶：mirror 当 authority） |

名字只差一个词（`add*MetadataMirrors` 活 vs `get*MetadataMirrorContract` 死）。**靠 caller 图判定，不靠名字。**

### 死镜像脚手架的结构 tell（I4）

- [ ] 注释/字段自述是 "consistency mirror" / "copies … the authority is X"？→ 镜像，删。
- [ ] 它重建一段 C 表达式/步骤数/intrinsic 名再 `==` 断言（验「发射器没改」而非语义）？→ 删。
- [ ] 它的**唯一历史消费者**是已删的 golden validator / golden test？→ 死，删。
- [ ] 它是 fail-closed 但出口只 `signalPassFailure` / 报错（路径已 disabled）？→ I7 债务残留，删。

### 安全删除方法（closed-graph + full-link）

1. 枚举整个簇，grep 全树确认 top-level 入口 **0 外部 caller**（def+decl 通常 = 2 refs）。
2. **按 symbol 删，绝不按行号删**（与活代码交错；行号边删边漂，重新 grep）。
3. 入口删完后用 `-Wunused-function` + **从头 full link** 逐层收掉新暴露的私有 static，直到 0 警告。link 是安全网：漏删的活引用会变 undefined-reference 把你拦住。
4. 任何 symbol 删了导致 link 报 undefined → **它不是死的，还原 + 报告**，别硬删。

### 不可触碰的边界（删之前先确认不在 diff 里）

- I8 export 路径：`exportMaterializedRVVEmitCToCpp` / `compileRVVGeneratedSourceToObject` / `mlir::emitc::translateToCpp` 委托 / `candidateValidationFn` 链 / `buildRVVSelectedBodyHeaderMetadataEvidence`（活的 header 证据表，进真 .h）。
- I7 guards：`containsForbiddenDirectCMarker` / `rejectForbidden*`（拒非法 metadata，留）。
- 活 capability model：`CapabilityModel`（legality/cost/dispatch 多处消费）。
- 删完 build 必须绿 + lit 不差于 baseline（删的是死码，行为应逐字不变）。

## 八、★重链纪律：信 lit 计数前先强制重链

**本仓 tablegen `.inc` depfile 路径重复 → `ninja` 永远重跑 tablegen，但不会因此重链 `bin/weft-opt` / `bin/weft-translate`。** 结果：改了 `lib/Conversion` / `lib/Target` 后 `ninja` 退 0、libs 重建，但**工具仍链旧 lib** → lit 跑 stale 二进制 → **假绿**。`touch source + ninja` **不够**。

**改了发射器 / 验证器 / 删了 owner 后，唯一可信：**

```
rm -f build/bin/weft-opt build/bin/weft-translate
(cd build && ninja bin/weft-opt bin/weft-translate)
# 确认 weft-opt 时间戳 > libWeft*ConversionRVV.a / *Transforms.a，再跑 lit
```

**更狠的坑——改了 header/struct layout（如 `CapabilityDescriptor` 字段）**：depfile bug 让**别的 target 的 `.o` 不会因 header 变化重编**（depfile 根本没列那个 header）→ 旧 layout 的 `.o` 链新 layout 的 lib → `sizeof`/offset ABI mismatch → **运行时内存损坏 / 段错误**，build 还是绿的。`rm 工具` 救不了（test/plugin 的 `.o` 仍旧）。改 header/struct 后唯一可信：

```
(cd build && ninja -t clean && ninja && ninja bin/weft-opt bin/weft-translate)
```

注意 `ninja`（无参）**不建 weft-opt**（非默认 target）——clean 后必须显式 `ninja bin/weft-opt bin/weft-translate`，否则全部测试 exit 127（「几百 reds」的假灾难其实是工具没建）。

**推论**：

- **定 baseline 用 clean build 的真实数**，别照抄上一轮 agent 报的数。
- byte-exact gate 必须用 forced/clean rebuild + BEFORE/AFTER-EQUALITY。
- 错误**文案**漂移（如 golden validator 被删后验证器换措辞）会让 STALE-\*/golden CHECK **假红**——那是 stale 测试不是回归；同步措辞时保留 key + expected + actual，别弱化成 tautology。

## 九、测试形态（选哪种测试）

测试验证**真实编译器行为**：dialect syntax、verification、pass 行为、plugin construction
interface、exact typed-body consumption、公共 EmitC lowering、target artifact 打包，以及被
主张时的 runtime 证据。

**测试不是** dashboard、readiness 状态、artifact ledger，**也不是替代架构 authority**（[architecture](../architecture/index.md) I4）。

| 形态 | 用途 |
|---|---|
| **lit / FileCheck** | dialect syntax/parsing · verifier 成功/失败 · pass 重写行为 · fail-closed 诊断 · selected-body realization 与 exact artifact consumption 在 IR 中可见 · 公共 EmitC materialization |
| **C++ tests** | plugin registry API · family construction/artifact-driver API · selected-body realization 结果对象 · capability helper API · 非文本编译器工具 |
| **Runtime / Hardware Evidence** | runtime/correctness/performance 主张需要**真实执行证据**。RVV 即真 `ssh rvv` 输出（[architecture](../architecture/index.md) I8）。**本地 compile-only、静态 MLIR check、Python smoke 都不是** RVV runtime 证据 |

### 判断点（不是 gate）

- 测一条 MLIR 行为时，**优先 lit/FileCheck**；只有文本测不了的语义才上 C++。**Python 测试可验 tooling 脚本，但不替代 MLIR 行为测试**（[canon · 核心不变量](../canon/核心不变量.md) I6）。
- 加了库 / dialect / pass / 工具 / 测试后：**CMake configure/build 把它们都带进去了吗？**（漏 wire = 测试根本没跑，比红更坏。）
- 测试挂在**生产路径**的编译器改动上了吗？还是挂在 dashboard / 只读报告面上（后者违 [architecture](../architecture/index.md) I4）？
- 写"第 N 个 generated-bundle evidence 测试"前：它验证的是一条**新改动的** route 吗？还是在已验证过的 family 上重复刷证据（**枝节**，见 §一 反模式「无限证据 closeout」）？
- 主张性能前：有没有"先正确、后计时、且赢 baseline"的真 `ssh rvv` JSON？没有就别说快。（硬件证据通用契约与断言来源区分 → [canon · 正确性与证书](../canon/正确性与证书.md)。）

## 十、Quick Routing

- **选下一个 task / 怀疑自己在做枝节** → §一 主干纪律。
- 修改 target / profile / variant legality / dispatch / emission path → §二 能力优先。
- 准备新增一个 contract/owner/route → §三 复用优先（确认不是又一份重复模板）。
- 实现跨层特性 → §四 跨层数据流。
- 新增 op/dialect/pass 表达 → §五 计算边界。
- 新增 RVV/IME/offload/future extension → §六 插件局部性。
- 删 RVV 字符串机器 / route-validation / metadata-mirror 脚手架 → §七 去死镜像 + §八 重链纪律。
- 跑 lit 并要引用其计数 → §八 重链纪律（**先 rm 工具强制重链**）。
- 要加一个测试 / 拿不准该用 lit 还是 C++ → §九 测试形态。
