# 队列与简报

Trellis task 树是可选的协调工具，不是项目唯一队列，也不是开工许可。

## 一、何时使用队列

适合：

- 多阶段 program；
- 多 agent 或多 worktree；
- 明确的依赖图；
- 用户要求长期追踪；
- 正式实验 campaign。

不必使用：

- 单阶段、触碰集明确的修改；
- 当前会话内可完成的工作；
- 已有对话计划足够表达顺序；
- 只读检查。

## 二、队列权威范围

只有当用户明确采用某个 task 树作为当前 campaign 计划时，它才是该 campaign 的协调记录。

- 用户最新指令始终可以重排、收窄或终止该计划。
- issue 列表不是自动执行队列。
- task 状态不覆盖代码、测试和实验事实。
- 历史 ROADMAP 标记可以保留作 provenance，但不构成现行命名要求。

## 三、并行

并行是性能优化，不是合规目标。

- 独立、边界清楚、touch set 不相交时可以并行。
- 公共接口、schema、同一 emitter 或同一 spec 正本应串行整合。
- 没有有价值的独立子任务时，单线推进完全正常。
- 并行期间精确暂存路径，避免吸入其他 worktree 或 agent 的修改。
- worktree 可以承载未完成的中间态，但主线只接收符合 [architecture · 退役与原子合入](../architecture/退役与原子合入.md) [RET-1] 的完整 slice；不得通过合并顺序维持新旧双轨。

## 四、状态更新

长任务的更新应简短回答：

- 当前完成了什么；
- 发现了什么关键事实；
- 正在处理什么；
- 是否有需要用户决定的阻塞。

不强制固定七行模板，不要求每次报告头条数字，也不要求把所有剩余工作塞入队列快照。

数字若出现，仍需来自可复跑工具、主表或 run-id。

## 五、恢复上下文

恢复工作时按实际需要读取：

1. 用户最新请求；
2. 当前 git 状态；
3. 当前计划或 task；
4. 相关 spec；
5. 最近实现和测试。

不得只凭旧 task 恢复出一个已经被用户取消或重定向的世界。
