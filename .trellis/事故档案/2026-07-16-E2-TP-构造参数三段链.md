## 二 两条闭式（这是本节点的承重物）

### 2.1 q3_K@rvv：strip 宽度 / 展开因子

```
minVLEN    = deriveMinimumVLEN(march)                  RVVCapabilityProfile.cpp:289
half_lanes = (minVLEN < 128) ? 0 : min(minVLEN/16, 16) RVVLowerQuantContraction.cpp:916-921
             （kWeightInterleave = 16                  同文件 :160）
numHalves  = kWeightInterleave / half_lanes            同文件 :1423
```

`numHalves` 是**不相交 strip 数**，region 每条 strip 携带一个向量累加器 —— 它**字面就是每-strip 整数核的展开因子**，所以第三段可以在反汇编里把它数出来。

### 2.2 q4_0@ime：wide-vmadot 部署

```
fragBits = macM*macK*elem_in_bits = 4*8*8  = 256
accBits  = macM*macN*accum_bits  = 4*4*32 = 512
rpfIn    = max(1, ceil(fragBits / vlen_bits))
rpfAcc   = max(1, ceil(accBits  / vlen_bits))
rpfIn != 1                       => 能力腿 DECLINE → narrow fallback   IMEBackendEmissionDriver.cpp:474
vreg_floor(njw) = rpfIn*(1+njw) + njw*rpfAcc <= 32 ；取最宽 mechanized njw
                                                                        同文件 :444-497（表 :352-361）
```

## 三 实测结果（全部由 `tp_param_chain.py` 自己 emit，非散文裸数）

### 3.1 q3_K@rvv 第一段：事实 → plan 闭式参数（7 个 march 点全通）

Python 侧**独立重实现**闭式作为 oracle，与 `weft-opt` 实跑对拍：

```
  march=<empty>                    minVLEN=0     closed-form half_lanes=0   weft-opt=0   numHalves=-   OK
  march=rv64gc                     minVLEN=0     closed-form half_lanes=0   weft-opt=0   numHalves=-   OK
  march=rv64gcv_zvl64b             minVLEN=128   closed-form half_lanes=8   weft-opt=8   numHalves=2   OK
  march=rv64gcv_zvfhmin            minVLEN=128   closed-form half_lanes=8   weft-opt=8   numHalves=2   OK
  march=rv64gcv_zvl256b_zvfhmin    minVLEN=256   closed-form half_lanes=16  weft-opt=16  numHalves=1   OK
  march=rv64gcv_zvl512b            minVLEN=512   closed-form half_lanes=16  weft-opt=16  numHalves=1   OK
  march=rv64gcv_zvl1024b           minVLEN=1024  closed-form half_lanes=16  weft-opt=16  numHalves=1   OK
```

**为何这证明「闭式导出」而非「查表拍脑袋」**（三个判别点，缺一则弱）：

1. **clamp 区活着**：512 → 16、1024 → 16，**不是** 32/64。`min(·,16)` 项真的在起作用。
2. **fullV 地板活着**：`rv64gcv_zvl64b` → 8 而非 0 —— 因为 full-V 按批准 spec 强制 Zvl128b 地板（`RVVCapabilityProfile.cpp` 第 (2) 段），zvl64b 被地板抬到 128。查表不会有这种"低于地板反被抬升"的行为。
3. **无能力 → fail-closed**：`rv64gc` / 空 march → **根本不构造 repack op**（退化为 block-dot stub），不是"给个默认值"。

单点复跑：

```
build-weft/bin/weft-opt test/Conversion/RVV/rvv-emit-quant-contraction-q3-K-repack-gemm-prefill-vlen128.mlir \
  --weft-rvv-lower-quant-contraction=march=rv64gcv_zvl256b_zvfhmin | grep -o 'half_lanes = [0-9]*' | sort -u
# => half_lanes = 16
```

**旁证（plan 层 half_lanes 是唯一 VLEN 键控整数参数）** —— 整 plan 逐行 diff 只有 2 行（一改一）：

```
diff <(build-weft/bin/weft-opt <q3k fixture> --weft-rvv-lower-quant-contraction=march=rv64gcv) \
     <(build-weft/bin/weft-opt <q3k fixture> --weft-rvv-lower-quant-contraction=march=rv64gcv_zvl256b) \
  | grep -c '^[<>]'
# => 2      （唯一差异 = half_lanes 8 -> 16）
```

这条是**诚实收窄**：本格的「构造参数」在 plan 层就是**一个标量**，不是"展开因子/tile/累加顺序"三件套。tile（`tiling_variant`）此格恒 `plain`、累加顺序（`loop_order`）恒 `col_outer`，**都不由 VLEN 键控**。

### 3.2 q3_K@rvv 第二/三段：plan 参数 → 产物 → objdump

链路（**全本地，零上板**）：
`weft-opt --weft-rvv-lower-to-emitc` → `mlir-translate-20 --mlir-to-cpp` → `clang++-20 --target=riscv64-unknown-linux-gnu` → `llvm-objdump-20`

```
  march=rv64gcv_zvfhmin            half_lanes=8   numHalves=2   vwmacc.vx=2048   obj=q3k.rv64gcv_zvfhmin.o (115784 bytes)
  march=rv64gcv_zvl256b_zvfhmin    half_lanes=16  numHalves=1   vwmacc.vx=1024   obj=q3k.rv64gcv_zvl256b_zvfhmin.o (58808 bytes)

  CONSISTENCY: predicted numHalves ratio 2/1 = 2.0000
               observed  vwmacc.vx ratio 2048/1024 = 2.0000   ==> CONSISTENT
```

**一致性判定 = CONSISTENT**：plan 声称 VLEN128 要 2 条 strip、VLEN256 要 1 条；反汇编里每-strip 的展开 MAC（`vwmacc.vx`）正好 2048 : 1024 = **2.00 整**。

整体向量指令 10994 : 5496（≈2.0004），且逐助记符比值成排为 2.00。`vmv.v.i` 是例外（129/14，≈9.21）—— 那是常量物化、非每-strip 工作，**如实标出、不并入判据**。

逐助记符复跑（承接上一条命令产出的 `/tmp/q3k.$M.o`）：

```
for M in rv64gcv_zvfhmin rv64gcv_zvl256b_zvfhmin; do
  D=$(llvm-objdump-20 -d --mattr=+v,+zvfhmin /tmp/q3k.$M.o)
  printf "%-26s total-vec=%s vwmacc.vx=%s vwmacc.vv=%s vand.vi=%s vle8.v=%s vmv.v.i=%s\n" "$M" \
    "$(echo "$D" | grep -oE '\bv[a-z0-9_.]+' | grep -vE '^v[0-9]+$' | wc -l)" \
    "$(echo "$D" | grep -c 'vwmacc\.vx')" "$(echo "$D" | grep -c 'vwmacc\.vv')" \
    "$(echo "$D" | grep -c 'vand\.vi')" "$(echo "$D" | grep -c 'vle8\.v')" \
    "$(echo "$D" | grep -c 'vmv\.v\.i')"
done
# rv64gcv_zvfhmin            total-vec=10994 vwmacc.vx=2048 vwmacc.vv=128 vand.vi=768 vle8.v=224 vmv.v.i=129
# rv64gcv_zvl256b_zvfhmin    total-vec=5496  vwmacc.vx=1024 vwmacc.vv=64  vand.vi=384 vle8.v=112 vmv.v.i=14
```

复跑：

```
M=rv64gcv_zvfhmin   # 或 rv64gcv_zvl256b_zvfhmin
build-weft/bin/weft-opt test/Conversion/RVV/rvv-emit-quant-contraction-q3-K-repack-gemm-prefill-vlen128.mlir \
  --weft-rvv-lower-quant-contraction=march=$M --weft-rvv-lower-to-emitc \
| mlir-translate-20 --mlir-to-cpp \
| clang++-20 --target=riscv64-unknown-linux-gnu -march=$M -ffreestanding -O2 -c -x c++ - -o /tmp/q3k.$M.o \
&& llvm-objdump-20 -d --mattr=+v,+zvfhmin /tmp/q3k.$M.o | grep -c 'vwmacc\.vx'
# rv64gcv_zvfhmin => 2048 ; rv64gcv_zvl256b_zvfhmin => 1024
```

> `zvfhmin` 是**真 ISA 需求**不是凑数：q3_K 的 fp16 scale 解码用 `vfloat16m1_t`，缺 zvfh/zvfhmin 时 clang 直接报 `requires the 'zvfh or zvfhmin' extension`。板上 rvv 侧历史归档同样是 `rv64gcv_zvfhmin`。

### 3.3 q4_0@ime 第一/二段：vlen_bits 事实 → 闭式 → 发射叶

扰动**单一** in-IR 能力事实 `vlen_bits`（其余字节不动）：

```
  vlen_bits=128   closed-form: rpfIn=2 rpfAcc=4(unobserved) floor=None -> narrow fallback
                  emitted:     rpfIn=2 rpfAcc=None floor=None -> narrow fallback  leaf=narrow(no _w2 leaf)
                  verified 2 field(s) ['rpfIn', 'decision']; NOT OBSERVED (decline path prints no value): ['rpfAcc']   ==> MATCH
  vlen_bits=256   closed-form: rpfIn=1 rpfAcc=2 floor=7 -> deploy IME-VMADOT-TILE-W2
                  emitted:     rpfIn=1 rpfAcc=2 floor=7 -> deploy IME-VMADOT-TILE-W2  leaf=mac_kloop_w2
                  verified 5 field(s) ['rpfIn', 'rpfAcc', 'njw', 'floor', 'decision']   ==> MATCH
  vlen_bits=512   closed-form: rpfIn=1 rpfAcc=1 floor=5 -> deploy IME-VMADOT-TILE-W2
                  emitted:     rpfIn=1 rpfAcc=1 floor=5 -> deploy IME-VMADOT-TILE-W2  leaf=mac_kloop_w2
                  verified 5 field(s) ['rpfIn', 'rpfAcc', 'njw', 'floor', 'decision']   ==> MATCH
```

手算对拍（每个数都能笔算）：

- `vlen_bits=128`：`rpfIn = ceil(256/128) = 2 ≠ 1` → 能力腿拒绝 → narrow fallback，**且不发 `_w2` 叶**（拒绝行为可见、非静默）。
- `vlen_bits=256`：`rpfIn = ceil(256/256) = 1`；`rpfAcc = ceil(512/256) = 2`；`floor(njw=2) = 1*(1+2) + 2*2 = 7 ≤ 32` → 部署 W2。
- `vlen_bits=512`：`rpfAcc = ceil(512/512) = 1`；`floor(njw=2) = 1*3 + 2*1 = 5 ≤ 32` → 部署 W2。

**`rpfAcc@128` 如实标 unobserved**：拒绝路径在打印 `rpfAcc` 前就 return 了（`:474` 早退），所以该值虽由代码算出（`:458`）却**未被观测**，不计入已验证字段。此格只验了 2 个字段，工具明写。

**探针 `table_vs_live`（证伪"这只是查表"）**：

```
    static table W2 minVregBudget = 7 (IMEBackendEmissionDriver.cpp:355, the VLEN256 witness)
    live emitted floor @vlen_bits=512 = 5
    ==> DIVERGE: value is COMPUTED from the fact, not read from the table
```

静态表 `:355` 给 W2 记的 `minVregBudget` 是 **7**（VLEN256 见证值）；而 `vlen_bits=512` 时**实发** floor = **5**。**实发值与表内值分叉** ⇒ 该数是从事实**算**出来的，表里那个 7 只是文档。这是本节点对"闭式 vs 查表"最硬的一条判别证据。

**诚实边界**：`njw` 不随 VLEN 变宽（512 时 floor 降到 5、余量很大，仍选 W2）—— 因为 W4 在表里是 `measured-negative`（`:358`，board-measured full-matmul NULL），**被 mechanized 状态封顶**，不是闭式算不出来。闭式算的是 floor，**选择**还受 registry 状态约束。

### 3.4 第三段（objdump）for q4_0@ime：**BLOCKED-toolchain，未做未编**

```
clang++-20: error: invalid arch name 'rv64gcv_xsmtvdotii1p0',
            unsupported non-standard user-level extension 'xsmtvdotii'
```

上游 clang-20 **不认** SpacemiT 的 `xsmtvdotii` 非标准厂商扩展，本地无法产出 IME 叶的 riscv64 对象。要走通需 SpacemiT GCC-15.2 fork —— 它在 **k1 板**上。**本轮板时归 P 线（单实例铁律），故此段未执行、未伪造**，CSV 里记 `PENDING` / `BLOCKED-toolchain`。

## 五 反例与自检（本节点的可证伪性）

`tp_param_chain.py` 不是只会打勾的脚本。三条**负对照**（改坏 oracle 常量，跑 mutated 副本）：

| 负对照 | 改动 | 期望 | 实测退出码 | 首条报错 |
|---|---|---|---|---|
| A | `K_WEIGHT_INTERLEAVE` 16→8 | 失败 | **1**（0 traceback） | `q3_K leg1 march='rv64gcv_zvl256b_zvfhmin': want 8 got 16` |
| B | `IME_MAC_K` 8→4 | 失败 | **1** | `q4_0@ime vlen=128 rpfIn: want 1 got 2` |
| C | `K_VREG_FILE` 32→4 | 失败 | **1** | `q4_0@ime vlen=256 njw: want 1 got 2` |
| 基线 | 无改动 | 通过 | **0** | — |

复跑（`WEFT_REPO` 覆盖存在就是为了让 mutated 副本仍能定位真树）：

```
export WEFT_REPO=/home/kingdom/phdworks/TianchenRV
sed 's/^K_WEIGHT_INTERLEAVE = 16/K_WEIGHT_INTERLEAVE = 8/' tools/visibility/tp_param_chain.py > /tmp/negA.py
python3 /tmp/negA.py --print-only ; echo "exit=$?"   # => 1
```

**负对照 A 当场抓出脚本自身一个真 bug**：`half_lanes > kWeightInterleave` 时 `numHalves` 归 0，比值计算 `ZeroDivisionError` 崩溃（退出 1 是 traceback 的巧合，不是干净判负）。已修为显式失败分支，现 A 干净判负、0 traceback。**若无负对照，这个"看起来在把关、其实会崩"的洞不会浮出。**

确定性：连跑两次 CSV 逐行 diff = **0**。

## 六 措辞与口径纪律（自查）

- **零性能主张**：全文无计时、无倍数-vs-对手。`vwmacc.vx` 2048/1024 是**结构计数**，不是快慢。
- **★ 部署变体 ≠ 证过变体（本节点最大诚实边界）**：第三段 objdump 反汇编的是**本地 clang-20 `-O2` 交叉编译产物**，**不是板上出货二进制**（rvv 板出货 = gcc-15.2）。故本节点证的是「我方构造参数 → 我方发射结构」在**该编译路径下**一致；**"板上 shipped 对象是否同形"未证、属 board-pending**。不同编译器可能自行再展开/合并，这条不可外推。

- **收窄**：q3_K 的 VLEN 键控构造参数**只有 half_lanes 一个标量**（plan diff = 2 行为证），未声称"展开/tile/累加顺序"三件套均闭式导出 —— tile 与 loop_order 在此格**不由 VLEN 键控**。
